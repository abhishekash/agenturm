Shows agent and session IDs, repo/project, lifecycle status, update age, pending wait, and task details. MCP server calls now link across start/result events, expose qualified Claude Code and Codex tool names, report completion/error status, and include all stored history in server counts. Agenturm

A terminal-first monitor and local telemetry receiver for AI agents. It discovers supported local agent sessions, then accepts OTLP/HTTP traces, logs, and metrics in protobuf or JSON from instrumented runtimes and the existing agent-harness JSONL format. The terminal cockpit shows agents, activity, MCP calls, traces, host processes, and metrics. Data lives in SQLite. The receiver uses Python's standard library (3.11+); the terminal UI uses Textual.

GitHub Copilot CLI telemetry

Copilot CLI can send its built-in OpenTelemetry traces and metrics directly to the cockpit receiver. Start agenturm in one terminal, then launch Copilot CLI from the project in another:

export OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:14318
export OTEL_EXPORTER_OTLP_PROTOCOL=http/json
export OTEL_SERVICE_NAME=github-copilot
copilot

Setting the endpoint enables Copilot telemetry. The CLI defaults to http/json; the protocol is shown explicitly here. The cockpit groups spans into sessions when Copilot supplies gen_ai.conversation.id and reports model usage, tool activity, and recognized hook, skill, compaction, truncation, and session lifecycle events. Tool records contain only fields the CLI exports; the MCP Calls view can identify a server or tool only when those identities are present in telemetry. Prompt and response capture is off by default in Copilot CLI; keep it disabled unless you intend to collect that content. Copilot's OTel settings and span/event schema describe the emitted signals and optional content capture.

Install and launch the terminal cockpit

Python 3.11+ is required. Install the published CLI in an isolated environment with uv tools:

uv tool install --force agenturm
agenturm

To try it without installing, run uvx agenturm. If uv is not installed, use its official installation instructions. If the installed command is missing from your PATH, run uv tool update-shell and open a new terminal. You can also install into an active Python environment with python -m pip install agenturm.

The cockpit opens Agents, Activity, MCP Calls, and Traces as primary views; use More or 5–7 for Host, Metrics, and Findings. Agents opens to Today: current work, sessions that need you, and reported completions awaiting human review. The filter also offers Running, History, and Errors. History includes earlier work, including yesterday’s unreviewed completions. Task-first rows have an evidence inspector. Its website-aligned Observation palette is the default; change themes with Ctrl+P. Findings provides a searchable, paged review queue with occurrence counts, evidence links, and direct navigation to the source trace. Session counts and live process counts are separate; approval reviews are hidden by default. The cockpit attaches to a receiver on 127.0.0.1:14318, or starts one there. Run agenturm for full-screen panels in your current terminal. From this checkout, python3 -m observatory also works without installation.

Continue work across sessions

Press b to open Saved tasks, then n to save the selected session as a task. Give it a title, workspace, and brief with your intent, decisions, and next step; Ctrl+S saves. A task keeps its ID and notes when you close Agenturm, change agents, or clear retained telemetry. You can also start a blank task without a connected receiver.

Open a saved task to Edit notes, Link the selected monitoring run, Capture Git changes, or preview a Handoff. Runs shows the exact associations and lets you unlink one. Link again to refresh a run's saved evidence. Token and reported cost totals cover linked exact runs only; session-only links do not contribute totals. Missing values remain unknown, and incomplete coverage is labeled partial. Cache counts are input breakdowns, not additional tokens or estimated savings.

Handoff previews the saved brief, workspace snapshot, linked runs, and recorded checks. Copy brief copies that exact preview. Write MD + HTML creates a new Markdown/HTML pair without overwriting existing files. Capturing Git reads the local repository only when requested; it does not run tests. Recorded check results do not prove the current changes pass. Read the saved-task guide for CLI examples, storage, capture limits, and privacy details.

Existing Codex and Claude Code agents

Local receivers automatically discover recent session files under ~/.codex/sessions and ~/.claude/projects (CODEX_HOME and CLAUDE_CONFIG_DIR are respected). Start the monitor with no agent filename or Python environment flags:

agenturm

It reads actual logged activity as files update, including already running sessions. Agents need no restart or configuration change. Source logs stay untouched. Select an agent for its status and latest action; press e for the zero-setup recorded-progress summary or s for its activity. When a session explicitly asks for a user reply or approval, the monitor points you to that agent's own terminal; it cannot submit the answer or approve actions for the agent.

Native session capture includes bounded text and content by default. Recognizable credentials and sensitive structured fields are redacted before storage; this is best effort. Opaque/encrypted reasoning, private reasoning text, binary payloads, process environments and credential files are excluded. Content is limited to 8,000 characters per activity record, with nested fields bounded to 2,000 characters and at most 60 entries. Source schemas and upstream truncation can leave gaps. Use serve --metadata-only or cockpit --metadata-only for a receiver that omits native message text, commands and results. This setting controls future ingestion and does not erase previously stored content.

The Working agents headline counts unfinished, actively observed turns and names their runtimes; total sessions and open host processes are separate. A quiet model/tool call does not become idle after 35 seconds. On Linux, exact open session-file matches provide process/child CPU and I/O evidence; shared working directories are never used to guess a session-to-process match. Token usage comes from records; input counts include repeated/cached context and are not a billable-cost estimate. Costs remain unknown when not reported. Model-call latency is marked unknown when the log has no start time.

Discovery scans every 10 seconds and tails discovered files every second. It selects up to 50 Codex/Claude Code/Pi files modified within the past 24 hours and up to 50 OpenCode sessions with recent session or message activity, importing at most the last 8 MiB initially per file. Pi sessions are read from $PI_CODING_AGENT_DIR/sessions (default ~/.pi/agent/sessions). OpenCode supports both the legacy message/part tables and current session_message records, including recent records whose parent session row is absent. Claude Code subagent transcripts under a selected session's subagents/ directory and Codex subagent rollouts use the same limits; linking never triggers an unbounded historical scan. If a limit is reached, the terminal health line reports how many sessions are outside the visible window. Summaries may cover only part of a long session. Codex response IDs, Claude message IDs, and Pi message IDs prevent duplicate usage entries on reread; older Codex cumulative token snapshots are handled separately. A version with a different log schema may expose less activity. GET /api/health reports discovery status, session/task snapshots, runtime metadata, source count, read errors, and skipped malformed records. GET /api/activity?limit=100&service=codex&domain=shell&q=... exposes a bounded, searchable activity view from the latest 100 observed traces. The terminal shows up to 100 recent events, with full trace investigation available separately.

Local discovery runs in the receiver. If you installed an earlier version, reinstall the CLI and restart that receiver to enable it. A cockpit attached to an older receiver cannot enable discovery there. Add --no-local-agents to serve or cockpit to disable discovery in a receiver started by that command. Receivers bound to non-loopback addresses do not discover local sessions automatically. Other agent products still need an adapter or OTLP export.

Resource usage

The terminal fetches live data every two seconds; session inventory, MCP, metrics, usage and findings are cached for five seconds. Filter and selection actions can wake the feed immediately. Collection continues independently, even when display updates are paused. Tables update changed cells instead of invalidating an entire row.

OpenCode polling skips unchanged databases between a 30-second lookback refresh; that periodic refresh ages old sessions out even when OpenCode writes nothing. When a database changes, unchanged messages are not normalized or written again. On schemas with part update timestamps, unchanged tool payloads are not loaded again; older schemas fall back to content comparison. Revision caches contain only fixed-size digests within the 50-session / 30-message import window, not retained tool outputs. Payloads are capped at 2 MiB per record and 16 MiB per poll; deferred records resume on later polls. Initial import still costs more than steady-state monitoring, and large histories or sustained telemetry can increase CPU, memory and database size.

Run python scripts/benchmark_resources.py for a repeatable synthetic reader benchmark (idle, unrelated database writes, and one changed tool). It uses a temporary database, not personal sessions. Results measure reader CPU, logical reads and span write counts; they exclude terminal rendering and derived Store work. Regression tests in tests/test_resource_usage.py and tests/test_opencode.py enforce polling, cache and redundant-write behavior without relying on hardware-dependent CPU thresholds.

OpenCode local database

On loopback, the receiver checks OpenCode's local SQLite database in read-only mode and lists recent sessions with their project, task title, model, and assistant-turn token counts. Recorded tool parts appear as trace spans; persisted todo checklists appear as progress events with completion percentages. MCP names are attributed when OpenCode records an explicit qualified server/tool name. The usual database path is ~/.local/share/opencode/opencode.db; XDG_DATA_HOME and OPENCODE_DB are honored. Reasoning parts are never read. Inputs and results follow the same bounded, redacted content policy as other native sources; pass --metadata-only to omit those payloads and task text. Discovery covers the 50 most recently updated sessions from the last 24 hours, up to 30 assistant messages per session, 200 tool parts per message, and 100 checklist items per session. Both legacy session metadata and V2 session_v2 metadata are supported, with V2 taking precedence for migrated IDs. User/assistant and idle-outcome records determine running, completed, interrupted, and failed status independently of the bounded transcript window. OpenCode's internal schema can change; use OTLP for a stable cross-version integration. Inactivity does not imply an approval wait.

Optional Python SDK capture

Native session discovery is automatic for supported local agents. For another Python agent, automatic SDK capture is a separate command-line workflow; the monitoring cockpit itself does not launch agents. Install the capture extra into the agent's environment:

uv pip install --python .venv/bin/python 'agenturm[auto]'
agenturm run --endpoint http://127.0.0.1:14318 --service my-agent agent.py

Replace the environment path, service name, and agent filename with your own. Arguments after agent.py go to the script; --module runs a Python module. If Goechala is already installed in the active agent environment, use python -m observatory run --endpoint http://127.0.0.1:14318 --service my-agent agent.py.

This launcher runs the selected script in that terminal and is intended for SDKs not already captured from local session records. Existing processes can send OTLP telemetry to the receiver. Python SDK prompts and responses are omitted unless you add --capture-content. Native session capture has its own --metadata-only receiver setting.

Capture an agent without changing its code

For Python agents that use supported model SDKs, install the automatic capture extra and run agenturm run from the agent's own environment. This is a separate terminal command; the monitoring cockpit remains read-only and does not start or control an agent.

For example, start a persistent local receiver on port 14318:

python3 -m observatory --db ./observatory.db serve --port 14318

Activate the Python environment your agent uses. From this checkout, install the automatic capture extra once:

python -m pip install '.[auto]'

From your agent's folder, replace python agent.py with:

python -m observatory run --endpoint http://127.0.0.1:14318 --service my-agent agent.py

Your script and its SDK calls run normally. The launcher detects installed OpenAI, Anthropic, and LangChain SDKs, attaches OpenInference instrumentation, and sends completed spans through OpenTelemetry to the local receiver. SDK versions must match the installed instrumentors; the launcher reports dependency mismatches before starting an unsupported setup. OpenAI-compatible endpoints such as local model servers are supported when your agent calls them through the OpenAI Python SDK. LangChain / LangGraph callbacks provide framework activity, and SDK calls inside a chain are linked to its trace when the framework does not attach runtime context.

Arguments after the filename are passed to your agent. Use --module before the target to run a package instead of a file. The launcher uses the active Python environment; install the auto extra in that environment. Restart existing agents through the launcher to enable capture. For other runtimes, use their OpenTelemetry export support or the manual clients below.

By default, automatic capture includes model metadata, reported tokens, duration, and errors. Select Include prompts and responses in the guide, or add --capture-content, to capture content too. Captured string attributes are limited to 4,000 characters. Token usage depends on what the model SDK returns; OpenAI chat streams need stream_options={"include_usage": True} for token counts. Costs remain unknown unless telemetry reports a cost.

Set OBSERVATORY_TOKEN in the agent's terminal when the receiver requires bearer authentication. The launcher checks the receiver before starting, sends a heartbeat while the agent runs, reports model-call start/finish progress, and flushes completed spans before marking the agent finished. Active model calls appear as RUNNING before their completed spans arrive, including when filtering by agent service. Each process has its own source ID, so connection counters distinguish agents even when they share a service name. An abrupt process exit becomes disconnected after its heartbeat expires.

To try automatic capture without API keys or paid model calls, the local replay example uses real SDK clients with in-memory responses:

python -m pip install '.[auto]' 'openai>=3' 'anthropic>=1.8' langchain-core
python -m observatory run --endpoint http://127.0.0.1:14318 --service local-capture-demo examples/automatic_capture_demo.py

The replay uses the current SDKs' httpx2 mock transport and records an OpenAI call inside a LangChain runnable, an async OpenAI stream, an Anthropic message, and an expected error. All model responses are local replay data. Telemetry goes only to your selected Goechala receiver.

Run

cd agenturm
python3 -m observatory --db ./observatory.db serve
# The root address is a plain-text receiver status page; use the terminal cockpit to inspect activity.

Set a retention window for long-running local deployments. The server prunes at startup and hourly; complete trace data is removed together, while unlinked logs, metric points, and endpoint inventory rows use their own timestamps:

python3 -m observatory --db ./observatory.db serve --retention-days 30

The receiver keeps trace parent IDs, attributes, events, links, resource attributes, instrumentation scope name, and status. Its endpoint inventory groups spans, logs, and metrics by host.id, host.name, device.id, or service.instance.id when producers include those resource attributes; it reports OS, architecture, user, environment, services, last seen time, and linked trace counts. Logs with a valid trace ID appear alongside that trace; agent.progress log events with agent.progress.stage and optional agent.progress.percent attributes also appear in its progress list; event.name and the equivalent progress.* fields are accepted as aliases. Gauge, sum, histogram, exponential histogram, and summary metric points retain their type, timestamp, attributes, unit, and available value or distribution fields, including the sum monotonicity flag that distinguishes counters from up/down sums; no-recorded-value points remain visible as missing readings and are excluded from charts. Cursor MCP aggregate metrics stay separate from recorded calls: delta counts are summed, while cumulative counters use the latest point per attribute/resource series, including after resets. service.name identifies each producer. Token counts use gen_ai.usage.input_tokens and gen_ai.usage.output_tokens, the harness's llm.usage.* fields, and OpenInference llm.token_count.prompt / llm.token_count.completion; OpenInference LLM and embedding model names, indexed chat messages, and embedding input/vector summaries are also recognized. Cache read/write input counts and reasoning output counts are retained as breakdowns when reported; these are subsets of headline totals and are not added a second time. Cost totals accept llm.cost.total, the prompt/completion cost components, and the existing harness aliases. Unknown prices are shown as unknown, rather than zero cost. See the OTLP exporter protocol configuration for SDK settings.

Tool spans with gen_ai.operation.name=execute_tool and gen_ai.tool.name (or common tool.name attributes) appear automatically in the activity ledger. OpenInference spans with openinference.span.kind=TOOL are included as tool activity too. For file, Git, shell, network, browser, or other actions that are not already spans, emit an OpenTelemetry span event named agent.activity or a correlated log with event name agent.activity. Set agent.activity.domain, agent.activity.action, agent.activity.subject, and agent.activity.result; optionally add agent.activity.actor. The trace view groups the activity ledger by subject, filters events by changes or errors, and links each item back to its source span or log. Activities with result blocked, denied, or policy_denied also create a review finding that opens at its evidence. For example, an instrumented tool can record span.addEvent("agent.activity", {"agent.activity.domain":"file", "agent.activity.action":"write", "agent.activity.subject":"src/app.py", "agent.activity.result":"success"}). Keep credentials and sensitive content out of subjects and event details unless you intend to retain them.

For Python agents that need manual instrumentation, the package includes a small synchronous and asynchronous client. Nested spans inherit their parent, progress is posted while the run is active, and completed spans are sent when the run exits. Pass resource_attributes to identify the host in the endpoint inventory; host identity collection is opt in:

import platform
import socket

from observatory import Client

telemetry = Client(
    service="research-agent",
    token="optional-bearer-token",
    resource_attributes={"host.name": socket.gethostname(), "os.type": platform.system().lower(),
                         "os.version": platform.release(), "host.arch": platform.machine()},
)

async def run_agent():
    async with telemetry.trace(task="Find current guidance", session_id="thread-42") as run:
        await run.aprogress("planning", "Choosing a search strategy", 10)
        async with run.span("tool.search", attributes={"tool.name": "search"}):
            await search_web()
        async with run.span("llm.call", attributes={"gen_ai.request.model": "my-model"}) as call:
            answer = await ask_model()
            call.set_attribute("gen_ai.usage.input_tokens", 320)
            call.set_attribute("gen_ai.usage.output_tokens", 85)
        return answer

The client uses the standard library, splits large traces into requests below the receiver 8 MiB limit, and is best effort by default, so telemetry delivery errors do not interrupt the agent. Set strict=True to raise delivery errors, or inspect telemetry.last_error. Exception messages are omitted by default; capture_exception_message=True opts in to recording them.

Current boundaries

This is a working local vertical slice, not an Origin equivalent. Automatic capture covers the supported Python SDKs run through the separate run command; existing processes need OTLP export or restart through that launcher. Other runtimes can send OTLP or use the clients. Managed endpoint collector deployment remains manual, and endpoint inventory depends on host identity resource attributes. It also does not provide team access controls. Session grouping depends on IDs emitted by the producer. Retention is optional and local; it needs operational validation under sustained ingestion. Findings use a small deterministic ruleset and need broader validation before operational use. Run counters are derived from stored spans; native metric points are shown separately without unsafe aggregation across metric kinds or temporalities. Progress can come from an explicit API event or a correlated agent.progress OTLP log. Summary metrics have no OTLP temporality field; Goechala marks their count and sum as implicitly cumulative. The protobuf decoder supports the OTLP fields displayed or stored here and skips unknown fields; it is not a general protobuf decoder. Metric exemplars link measurements back to their source trace and span when those IDs are present; histogram bucket charts show one latest distribution point for the selected instrument, with its source attributes shown.

Agent session overview

The terminal's Agents view puts Agent / project, Current task, Status, and Updated in a task-focused list. Task previews stay on one line; agent/project rows use two lines. On wide terminals the session inspector is on the right with only status and a short latest-action label, not command arguments or output. On narrower terminals it stacks below; compact terminals prioritize the list until you inspect. Full session IDs, working directories, branches (when recorded), models, and usage remain available in the expanded inspector rather than taking up table columns. Press Enter to inspect; e expands the details and s opens session activity. Raw output and long values remain available in the selectable, copyable expanded detail pane and Activity. The default view does not repeat the activity table or show an unconfigured AI-summary button. Internal reviews are hidden from native sessions and stored session summaries alike unless Reviews is enabled.

The compact framed overview sits above a separate Views frame and scope controls. Working agents and Needs attention have separate summary areas; attention includes explicit input requests, possible stalls, and recorded failures, not ordinary tool waits. Press 1 for Agents, 2 for Activity, 3 for MCP Calls, or 4 for Traces. MCP details, token usage, and process inventory remain in their dedicated views. Wide terminals show all seven view tabs; narrower terminals expose 5 Host, 6 Metrics, and 7 Findings in the highlighted Other views selector. Very narrow terminals use a single labelled view selector for all seven destinations. Search stays with its evidence view, and keyboard hints stay at the bottom. The agent list has no fixed row or height cap: it and the inspector fill the remaining workspace, with additional sessions reachable by scrolling. Short terminals use a compact summary to preserve room for evidence.

Square, single-line panel edges and aligned headers separate the workspace without extra toolbars. An amber ▸ marks the selected session. Status uses shape and wording as well as color: ● working, ◌ quiet work, ✓ completed, and ! for input requests or status warnings. Completed rows keep a muted status rather than competing with live work. Selection retains these colors in every theme.

In Activity, select an agent with the Scope control (or press s on its row in Agents), then click Prompts beside Errors. This shows only recorded user messages for that agent, newest first; use ] to page backward through older prompts. Turn Prompts off to return to the full activity stream.

Status comes from native lifecycle records: Working, Waiting, Completed, or Interrupted. A known input request shows User input; a pending tool shows Tool response and its name. Unfinished turns with quiet logs show Quiet work (Working (quiet) in the expanded inspector); CPU/I/O progress from an exactly matched session process or its children can support Processing or Tool running. These are activity signals, not proof that a model request is making useful progress. Explicit approval/input waits persist until resolved.

After at least five minutes without records or observed process progress, a matched live session shows May be stalled (Possibly stalled in the expanded inspector), not a definitive hang. Without a process match, the status is Unconfirmed instead. Monitor delayed or Catching up identifies collector delay/unread data, not an agent failure. Details explain the status evidence. New transcript headers without started work are not counted as working. Completed turns stay completed even if their terminal process remains open. Unrecognized/missing lifecycle records remain Unknown. SDK connections report connection state separately.

The MCP Calls view includes configured server names discovered in known local Codex, Claude Code, Cursor, Gemini CLI, GitHub Copilot CLI, OpenCode, and VS Code configuration files, alongside servers with calls in the stored scope. Configured-only entries are labeled Configured; this is a name inventory and does not check whether a server is reachable or running. Only server names, client, and scope are retained or returned; commands, arguments, URLs, headers, and environment values are discarded. Select a server and press Enter to search its calls. Counters include older calls beyond the current page; the table's count describes the displayed page. The view reports a count when a known configuration file is unreadable, malformed, or over the 1 MiB scan limit; it does not expose the path or contents of that file. OpenCode project opencode.json and opencode.jsonc files support both the top-level mcp layout and the nested mcp.servers layout. For a running local OpenCode process, the monitor checks its working directory for project config. Claude Code and Codex qualified names (mcp__server__tool) and Codex explicit MCP completion records carry server/tool identity. Restart the receiver after upgrading to re-read discoverable local session files; the existing 24-hour discovery window and bounded file reading limits still apply.

Optional AI summaries

Every session first shows a local Progress summary · recorded activity. It needs no provider, key, or extra setup and never guesses the agent's remaining tasks. If OPENAI_API_KEY is already set in the terminal environment, optional AI summaries use that key with OpenAI's Chat Completions endpoint and gpt-4.1-mini by default. In Agents, select a session and click AI summary to request one. Otherwise, the local summary stays available without setup. The request sends its task, project, reported state, waiting reason, observed trace/span totals, token counts, error counts, cost coverage, and up to 30 recent action headlines to your chosen provider. It uses your API quota. Unavailable totals are sent as unknown rather than zero. Raw tool payloads, working directories, hidden reasoning, and environment values are excluded. Recognizable secrets are redacted, but task/headline text may still contain private project information. Only enable this with a provider appropriate for that data.

For another OpenAI-compatible provider, set these in the terminal that launches Goechala:

export OBSERVATORY_SUMMARY_URL='https://api.openai.com/v1/chat/completions'
export OBSERVATORY_SUMMARY_MODEL='YOUR_MODEL_ID'
# The existing OPENAI_API_KEY is reused unless OBSERVATORY_SUMMARY_KEY_ENV selects another variable.
agenturm

The URL is the full Chat Completions endpoint, and the model must be available to your account. Other compatible providers can use their endpoint, model, and API key variable. The default key variable is OBSERVATORY_SUMMARY_API_KEY. A compatible local server can use an HTTP localhost URL without an API key. OPENAI_BASE_URL and OPENAI_MODEL are also respected when reusing OPENAI_API_KEY. No key is saved to the database. The request uses max_completion_tokens and store: false; compatible providers must support those fields. See the API request schema.

Summaries run only on request, in the background, with a 12-second timeout. An unchanged snapshot reuses its summary for the lifetime of the UI; new session activity marks it as an earlier snapshot. Provider failures leave the local progress summary available. Generated text is labeled and does not override recorded status. Internal approval reviews are excluded.

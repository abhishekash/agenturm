Is Agenturm useful to developers running 20–50 agents?

Yes, for reducing the effort of reviewing concurrent agent work—not for orchestrating it. Its strongest practical job is answering: “This agent says it is done. What recorded evidence supports that, for this particular execution?”

Reviewed commit a601ad2236f22ef75600129e920ff763883bee7c, matching GitHub main when checked. Based on source inspection, documentation, and 38 locally executed focused tests. Not a firsthand 50-agent production trial or an adoption study.

One practical use: review a completed fix before integrating its branch

Imagine 30 local agents working in separate worktrees. One is fixing refresh-token retries. Several finish while you are reviewing another change. You no longer remember which terminal contains which test result.

An illustrative captured sequence for the retry worker:

TimeRecorded event
10:04pytest tests/test_retry.py -q finishes with exit code 0.
10:06The worker edits retry.py again.
10:07The worker reports “Done; tests pass.”

The problem is not that the test result is false. It is that it predates a later change. A completion message compresses away that distinction.

  1. Run uvx agenturm in an extra terminal. Supported recent native records are discovered without restarting those coding agents.
  2. In Agents → Today, select the retry task under Ready for review. Open its inspector and choose Review from Overview.
  3. Inspect captured checks and modifying operations. Agenturm can show the passing command followed by later recorded edits, scoped to the selected worker/execution, and suggest inspecting those edits and rerunning affected checks.
  4. Return to that worker’s original terminal/worktree. Review the diff and rerun necessary checks there. Integrate only after normal review. Mark the run reviewed in Agenturm to clear it from Today, not to certify correctness.

Why this earns a place beside your terminals: a common review surface replaces manual reconstruction across transcripts. Exact ownership matters: a sibling worker’s passing command must not become this worker’s validation. Native terminals can show the same evidence; the potential advantage is less reconstruction across concurrent runs and runtimes, not exclusive access to it.

Hypothetical scenario backed by implemented behavior and synthetic tests, not a customer outcome. Review exists in 0.2.3. The noninteractive agenturm review receipt command is main/Unreleased, not part of the published 0.2.3 install.

What I verified

  • workflow_evidence.py separates recorded checks, assistant claims, modifying operations, errors, and coverage. It compares edit timestamps with check completion timestamps.
  • ExecutionScope.matches constrains evidence by producer, worker, session, and run/turn. It does not combine everything from the same repository.
  • session_status.py distinguishes quiet work, explicit waits, collector backlog, and possible stalls. Silence alone is not proof of failure.
  • 38 tests passed in 3.115 seconds: session status, work receipts, and pure workflow-evidence cases. A real authenticated loopback receiver test excluded parent/sibling evidence, preserved a later-edit observation, and exported a frozen receipt. It was synthetic, not 30 live agents.
uv run --frozen python -m unittest tests.test_session_status tests.test_work_receipts tests.test_workflow_evidence.EvidenceTests -v

Why this is not yet a proven 50-agent cockpit

  1. Coverage is bounded. JSONL discovery selects up to 50 recent sources across Codex, Claude Code, and Pi; OpenCode separately selects up to 50 recent sessions. Historical and delegated sessions can consume those windows. This does not guarantee every one of 50 active agents is represented. Check collection diagnostics before trusting the roster.
  2. Performance remains open. The retained-history report measured 112.96 seconds cold readiness and 15.90% of one CPU core for an idle complete monitor on its synthetic 35-day fixture. A separate 20-minute soak reported rising RSS; memory stability was not established. These are repository-reported results on older named revisions, not measurements repeated on the reviewed head or predictions for your laptop.
  3. It observes; it does not enforce. It does not launch agents, answer approvals, isolate worktrees, prevent overlapping edits, independently attest commands, or prove today’s files match a captured test run. No later recorded edit does not establish freshness. CI and actual review remain necessary.
  4. Value is plausible, not measured. Reduced reconstruction time and mistaken verification conclusions remain explicit pilot hypotheses. Implementation evidence is not repeat adoption or quantified time savings. Local capture also creates a sensitive extra copy of agent content; redaction is best effort.

Recommendation

A review inbox for parallel coding work: “See what supports each agent’s ‘done’ before you integrate it.”

That is a concrete engineering decision, not another activity dashboard. For one agent, the extra surface may be unnecessary. For many concurrent sessions, trial this workflow before adopting it as an always-on monitor.

Use comparable batches of completed runs, with and without Agenturm. Measure time to find the correct execution, identify whether a recorded check preceded a later edit, and choose the next action. Track wrong-worker conclusions and missing capture as well as speed. If the inbox does not improve those decisions, the dashboard alone has not earned its overhead.

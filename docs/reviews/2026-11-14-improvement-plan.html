Proposed improvement plan · Based on reviewed source a601ad2 · Not implementation authorization

Close the action loop.

Make Agenturm the quickest reliable way to find which agent needs you, understand why, and return to the right place. Beat terminal scanning, native notifications, and duplicated notes—not an abstract competitor feature list.

All acceptance criteria below are proposed targets, not measured outcomes or current guarantees.

1. First delivery: make attention actionable

The smallest coherent product improvement should come before more integrations.

  • Promote the existing w inbox through a visible Needs you control at 80×24 and 60×18. Do not create a duplicate queue or force a new top-level navigation model.
  • Distinguish requests, failures, and completion reviews. A completion can wait; an explicit input request is blocking work. Ordinary tool waits should not all generate alerts.
  • Show the task, project, reason, recorded age, freshness and captured request excerpt. Label missing timestamps/content honestly.
  • Move verified terminal return out of Settings and beside the selected request. Keep Settings for notifications and thresholds.
  • Route only to an exact verified target. Otherwise explain the limitation and provide an appropriate supported fallback. Stopped Codex/Claude sessions may offer a copied resume command; never duplicate a live session.
  • Preserve selection and order during updates. A new incident must not move a different terminal under the cursor.

Proposed acceptance: find Needs you within five seconds at 80×24; inspect a selected request and invoke an available verified terminal route within three activations. Unsupported routing is explicit. Seen stays different from approved/resolved.

2. Second delivery: decision-ready completion review

Keep the scoped evidence engine. Improve presentation instead of adding another dashboard. Lead with four answers:

  1. What did this execution attempt?
  2. Which recognized checks and results were captured?
  3. Were modifying operations recorded after those checks?
  4. What should I inspect or rerun next, and what evidence is missing?

Keep source references and raw details behind the summary. Distinguish agent claims, recorded exit codes and unknown results. Make the return to the same inbox selection and the review acknowledgement path explicit. An acknowledgement never certifies correctness.

Proposed acceptance: users distinguish sibling results, checks followed by edits and partial capture without reconstructing transcripts. Never show a green “verified” badge merely because no later edit was captured. Metadata-only capture cannot supply content-based review.

3. Release gate: earn the always-on promise

Run this in parallel with UX work, before a reliable 50-agent marketing claim.

  • Benchmark receiver, collectors and terminal together under sustained 20- and 50-agent workloads with retained history, request transitions, delegated workers and errors.
  • Separate interactive readiness from completed indexing, keypress latency from event age, and whole-monitor CPU from Store-only CPU.
  • Test beyond recent-source windows. Expose omissions, backlog and stale capture; do not blindly increase every limit.
  • Profile retained allocations and run multi-hour fixed-load memory validation. A short functional pass is not stability evidence.
  • Preserve authentication, private storage, capture-policy enforcement and explicit export consent.

Candidate gates: existing repository targets of cold readiness below 30 seconds and idle CPU below 5% of one core on a named fixture; no unexplained sustained RSS growth under fixed retained load; declared coverage and freshness under the nominated active workload. Publish failed runs and raw results too. These are targets to validate, not current promises.

4. Then: lightweight continuation

Keep saving optional, offered at interruption, restart or runtime switch. A small reviewed handoff needs:

  • A constraint to preserve.
  • A decision and rationale worth keeping.
  • The next action.
  • The exact linked run and relevant evidence.

Reuse existing briefs, decisions and exports. Prefill editable source-backed drafts where appropriate; do not infer accepted decisions or silently send context to another agent. Replace duplicated notes, not the engineer’s entire task-management system.

What not to build next

No renderer rewrite without a demonstrated blocker. No new top-level telemetry tabs. No automatic approval, guessed terminal targets, quota claims derived from token totals, or general-purpose swarm orchestration. AI summaries must not be necessary to understand the default view.

How we know it is better

Compare with the same users’ current terminal/notification/notes workflow. Measure request-to-native-response delay, manual status checks, time to find the correct execution and next action, wrong-worker conclusions, false alerts, missed waits and voluntary repeat use. Separate collector delay from human delay. Missing timestamps remain unavailable. Test interruption recovery separately.

Delivery order: actionable inbox and terminal return; concise completion review; performance/coverage gates throughout; lightweight continuation after observed demand. Update README, walkthrough, help and release notes to describe the same shipped workflow. Keep unreleased features clearly labeled.

Does Agenturm remove attention and reconstruction work—or become another thing the engineer must monitor?

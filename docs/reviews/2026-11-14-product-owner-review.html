Useful work,
not more monitoring.

Agenturm source reviewed: a601ad2236f22ef75600129e920ff763883bee7c. This review revisits the earlier developer-value document using code inspection, focused tests, and a synthetic terminal workflow probe.

Product decision

Agenturm’s credible primary job is helping an individual engineer direct their attention across concurrent local coding agents. Completion review strengthens that job; saved tasks help when work outlives a session.

Which agent needs me → why → return to the correct session → review its result → carry the task forward if necessary.

My previous review correctly identified completion evidence as useful, but made it the whole positioning. That is too narrow. “A passing test followed by an edit” demonstrates trust; it does not establish the most frequent reason to open the app. The repository’s existing qualitative research already makes the stronger distinction: attention is the entry point, review supports the decision, continuity preserves the work. This remains a product hypothesis, not measured adoption.

Recommended promise: “Know which agent needs you, why, and where to return.” Supporting promise: “Review what happened and carry the task forward.”

Who the primary user actually is

The engineer personally responsible for several concurrent agent tasks and the resulting code. They already have terminals, review diffs, and decide what to integrate. Their problem is fragmented attention and context reconstruction—not a lack of charts.

Recruit ordinary multi-session engineers first, with a separate power-user cohort. 20–50 agents is a stress case to validate, not the customer definition or a proven capacity claim. Concurrent decisions matter more than a large process count.

How it becomes useful in a working day

One illustrative task: a retry fix delegated while other agents do unrelated work.

  1. A recorded input request arrives. The inbox separates requests from ordinary tool waits and completions. Prioritize responding instead of repeatedly scanning terminals.
  2. Recover enough context to answer. Inspect the request and evidence. The existing Linux/tmux return action can select a pane where an exact process mapping exists. Otherwise use the disclosed fallback and native terminal. Do not pretend every runtime or terminal can be routed.
  3. Observe advancement. Fresh positive evidence resolves the request. Marking it Seen does not approve it or establish resolution.
  4. Review reported completion. Inspect recorded checks, edits, failures and gaps before choosing what to inspect or rerun. A sibling’s success is not this execution’s validation. Diff review and CI remain necessary.
  5. Preserve only work that needs continuation. Save “do not change the public API,” a rejected approach and rationale, the next action, and linked evidence. Preview before handing it to another agent. This is explicit context maintenance, not automatic memory restoration.

The potential benefit is less time choosing a terminal and reconstructing a task before acting. Not more running agents, guaranteed faster shipping, authoritative provider quota, or independent verification.

The code contains the right foundations

  • Trustworthy state distinctions: session_status.py separates explicit requests, quiet work, process progress, collector delay and uncertainty. False “stuck” claims would destroy trust.
  • Incident identity, not just badges: attention.py and ui_workflow_controller.py retain unresolved incidents, suppress initial-inventory alert storms, and distinguish acknowledgement from native resolution.
  • Scoped evidence: workflow_evidence.py isolates receiver/producer/agent/session/run or turn, separates claims from checks, and discloses partial capture. This adds substance beyond a notification bell.
  • Reading continuity: stable IDs, deferred reordering, background reads and frozen exports let engineers read while agents continue. These are product features.
  • Durable human intent: saved tasks retain briefs, versioned decisions, linked runs and bounded Git captures separately from telemetry retention. Revision conflicts refuse to overwrite newer work.
  • Low adoption dependency: supported native discovery and recorded summaries need no Agenturm account or model call. Capture still creates sensitive copies; best-effort redaction is not a confidentiality guarantee.

Concrete product findings

High 1. The attention path is less prominent than the inventory

Observed: 50 synthetic sessions—44 running, two waiting, one failed, three completed—remained in the roster at all tested sizes. Today deliberately orders running work first. The first wait appeared at row 45, below the initial viewport. The existing w inbox immediately narrowed the work to six relevant incidents, with an input request first.

This is not dropped data. It is discoverability: the overview is easier to find than the decision queue. Headers, help and the palette mitigate the problem but do not make the queue the obvious next step.

Recommendation: a persistent, activatable “Needs you” entry, discoverable at compact sizes. Reuse the inbox. Do not add a tab or silently move rows while someone reads.

High 2. Returning to the agent is treated like a setting

Observed: Terminal and Resume are children of Workflow’s Settings panel. At all three tested sizes that parent stayed hidden until Settings was activated. Main inspector actions emphasize Review, Activity and Trace instead.

Recommendation: contextual “Go to agent terminal” beside an input request when the target is verifiable; a supported resume-command fallback for stopped Codex/Claude sessions; honest unavailability otherwise. Preserve exact-process and PID-reuse protections. Do not guess by directory, send keystrokes, approve requests or launch duplicate sessions.

This promotes an existing capability. It does not claim terminal return is missing or universally supported.

High 3. Always-on monitoring must earn its resource and coverage claims

Discovery uses bounded recent-source windows: 50 JSONL sources across Codex/Claude/Pi and separately 50 OpenCode sessions. Historical/delegated records can consume them. Coverage warnings and diagnostics exist; they are not a guarantee that all 50 active agents will be observed.

The repository’s retained-history report records 112.96 seconds cold readiness and 15.90% of one core at idle on a synthetic 35-day fixture. A separate older 20-minute soak did not establish RSS stability. These are previous named-revision measurements, not new measurements of this checkout.

Recommendation: gate the 20–50-agent promise on readiness, idle CPU, sustained memory, event-to-display age and source omissions. Separate input responsiveness from collection freshness. A 50-row UI probe or 1,010-node hierarchy microbenchmark is not a live-workload benchmark.

Medium 4. The useful loop has avoidable seams

Today, Workflow, Review, Findings and Saved tasks serve legitimate purposes, but users must learn several nouns and acknowledgement meanings. Review opens evidence; Reviewed/Seen acknowledges; approval happens in the native terminal. Review offers save/export actions, while acknowledgement happens outside it.

Recommendation: preserve shortcuts but make the reading path explicit: request → native terminal; failure → recorded failure; completion → inspect evidence. Distinguish “Inspect evidence,” “Mark reviewed,” and “Seen; still pending.” Keep MCP/traces/findings as investigation depth. An acknowledgement is never a merge-readiness gate.

Medium 5. Documentation explains contracts better than first value

The README leads with attribution/completion; research leads with attention. The older UX spec describes All/Attention/Working/Finished while code and usage describe Today/Running/History/Errors. The earlier review added another narrative instead of reconciling them.

Recommendation: one current product contract and a short first-run path: existing agents → real request or completion → inspect → return to native terminal → observe the outcome. Keep careful evidence/privacy contracts behind that path. Clearly separate main/Unreleased receipts from published 0.2.3. This assessment does not change those files.

Medium 6. Saved tasks must not become compulsory bookkeeping

Structured decisions, offline editing and reviewed handoffs exist. Their value depends on explicit human maintenance. A full task record for every small run could erase the benefit.

Recommendation: save at interruption/restart/handoff, not before monitoring. A minimal constraint, decision and next action with source links may suffice. Keep drafts editable and consent explicit; do not infer accepted decisions or silently inject context. Test whether it replaces a notes workflow rather than creating another task manager.

Test whether primary users actually benefit

Run a small consent-based pilot with multi-session engineers, varied runtimes, and a separately reported 20–50-agent cohort. Compare the same jobs with their notifications/tmux/notes setup and Agenturm; counterbalance order where practical.

  • Measure recorded request → native response/advancement, separating detection delay from human delay. Missing timestamps/signals mean unavailable duration.
  • Measure time to identify the correct execution and an appropriate next action. Count wrong-worker and false-verification conclusions.
  • Track manual terminal checks, irrelevant alerts, missed waits and omitted sources. A quiet inbox is not proof of zero misses.
  • Measure resumption time and preservation of constraints/rejected approaches.
  • Observe voluntary repeat use and which script or notes workflow can be retired. Screenshots and token totals do not establish productivity.

Proposed usability gates—not measurements: find the actionable queue within five seconds at 80×24; reach a recorded request and its verified terminal route within three activations excluding list navigation; do not mistake Seen for approval or completion for validation. Include unsupported routing and source omissions. Keep pilot records local or explicitly reviewed before sharing.

Validation and limits

  • 47 tests passed in 58.866 seconds across attention, Workflow, Today outcomes and task continuity. Included headless keyboard/resize paths and mocked exact tmux routing. SQLite ResourceWarnings and asyncio slow-task diagnostics appeared; no assertion failed. They do not establish a product memory leak.
  • A separate 50-session synthetic probe checked roster retention, inbox ordering, compact hints and Settings visibility at 120×36, 80×24 and 60×18. All 50 rows remained available; six relevant incidents appeared in the inbox. Not a live ingestion or performance test.
  • The prior review’s 38 passing tests covered status and receipts, including an authenticated loopback receiver. Separate focused batches, not a full-suite result.
  • No participant research, provider calls, actual notification delivery, live terminal switching, production benchmark, clipboard validation, or every-emulator visual inspection. No product code, shared worktree, running agent or remote branch changed.

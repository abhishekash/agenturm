Agenturm · Engineering validation · 28 November 2026

Indexed history instead of full-store sorts

Diagnosis

The running native 0.3.15 process showed about 170% CPU (100% is one logical core), while the host had approximately 9 GiB available memory and no swap use. A read-only investigation found about 1.7 million observations in a 1.3 GiB database. Selecting just 256 recent records took 4.342 seconds in one diagnostic sample: SQLite scanned observations and built a temporary sort.

Navigation, workflow notification checks, and background collection share this read path. A small result limit did not bound the database work. No personal observation content was exported; the live database was not modified.

Change

  • Schema 28 adds ordered time and source/time indexes.
  • Direct session and cursor predicates allow indexed seeks; exact source/session reads use the existing session index instead of walking unrelated newer sessions.
  • A sparse source/session/kind/time index finds lifecycle and relationship facts without searching every message or tool record when a relationship is absent.
  • The writer upgrades recognized databases transactionally under its existing lease. Read-only archive inspection does not migrate.

Observation identity, authorization, snapshots, correction revisions, cursor ordering, retention, and content grants preserve their existing semantics. Older read-only stores and grant-preserving migration are tested.

Reproduce

cargo test -p agenturm-store --locked history_read::tests
cargo test -p agenturm-store --release --locked \
  history_read::tests::benchmark_history_pages -- --ignored --nocapture

Each invocation creates and removes a temporary database with one million synthetic metadata records. Set AGENTURM_BENCH_ROWS for another size. The process measures the same store without and then with indexes, warms the queries, takes 12 samples per 256- and 16,384-record page, and compares complete results. It reports index-build time and database growth. Bulk seeding does not measure ingestion. These are warm query samples, not production percentiles or cold-cache measurements.

Local measurement

Linux 7.0.0 x86-64, Intel i7-1165G7 (8 logical CPUs), 15.7 GiB RAM; Rust 1.100.0 release build and bundled SQLite. One million synthetic metadata records, 12 warm samples per case:

ReadWithout indexes: median (min–max)Indexed: median (min–max)
256 records6,606.544 ms (3,352.880–9,896.085)2.012 ms (1.914–3.265)
16,384 records5,904.269 ms (3,522.262–10,368.278)71.861 ms (69.016–129.634)

The 256-record page fell from 999,999 full-scan steps, one sort, and 52,002,382 VM steps to 256 scan steps, no sort, and 12,404 VM steps. Index construction plus checkpoint took 3,192.5 ms. Database size grew from 208.61 to 295.44 MiB: 86.83 MiB extra.

Other desktop processes and concurrent workspace/release compilation were active. The wide baseline range is not an isolated-machine latency result. Exact page equality and deterministic work reduction are stronger evidence than a speedup ratio. The timing command's peak RSS includes compilation; it is not Agenturm app memory.

The full local workspace suite passed, including 183 UI and 158 Store tests (one opt-in benchmark excluded). Workspace/all-target Clippy passed with warnings denied. Some process-adapter integration tests need explicit binary paths; CI additionally exercises those configured paths.

Deterministic regressions

A 50,000-record fixture exercises recent, source-only, deep older-page, exact-session, and absent-session reads through the Store API. A 64-record page must perform no SQLite sort, at most 65 full-scan steps, and fewer than 50,000 VM steps. An absent relationship lookup must use the sparse fact index, perform no full scan or sort, and use fewer than 100 VM steps. These are work limits, not timing assertions.

Limits and upgrade

This removes a measured database bottleneck. It does not establish whole-app idle CPU, ingestion throughput, peak RSS, terminal rendering cost, or keypress-to-frame p95. Session-catalog aggregation still scans session evidence; sparse projections can examine many nonmatching records. Extra indexes consume disk and add write work. Their first build can delay startup on a large history.

Stop older Agenturm versions before upgrading a shared store. Schema 28 is not readable by 0.3.15. This fix ships in 0.3.16; 0.3.15 does not contain it.

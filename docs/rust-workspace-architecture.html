Rust workspace and plugin architecture

Agenturm uses one root Cargo workspace. Crates live under crates/, grouped by architectural responsibility instead of collected in one flat directory. A crate represents a cohesive API or implementation boundary.

Layout

crates/
├── applications/   # CLI, terminal UI, OS service
├── core/           # Kernel and wire contracts
├── domain/         # Pure reducers and bounded queries
├── plugins/
│   ├── api/         # Extension-specific contracts
│   ├── capabilities/# Capability providers
│   ├── connectors/  # Connector implementations
│   ├── fixtures/    # Executable protocol fixtures
│   ├── harnesses/   # Provider-specific agent readers
│   └── host/        # Discovery, supervision, source runtime, trust gates
├── storage/         # Store and storage-service boundaries
└── test-support/
    ├── fixtures/   # Synthetic golden inputs
    └── plugins/    # Test-only extension packages

The root manifest discovers crates with family-specific workspace globs. Put new production crates in the relevant family rather than at repository top level. Standalone fixture workspaces are reserved for isolation tests.

Dependency direction

applications ──compose──▶ plugin host ──uses──▶ providers
      │                         │                  │
      ├──▶ core contracts ◀─────┴──────────────────┘
      ├──▶ domain
      └──▶ storage ◀──────────── plugin host

test-support ──supports tests only──▶ crates
  • Core contracts (agenturm-kernel, agenturm-protocol) define host-owned facts, traits, and wire shapes. Provider parsing and policy do not belong there.
  • Plugin host owns supervision, bounded source runtimes, and host-side trust/admission checks. It depends on contracts and host-owned storage packages, not every provider implementation.
  • Providers are grouped by kind. Harnesses parse native formats; capability and connector crates implement their extension surfaces. They use shared contracts instead of adding provider-name branches to generic code.
  • Applications, domain, and storage stay separate: applications compose providers, domain crates remain provider-independent, and storage owns durable state and admission boundaries.
  • Test support holds synthetic fixtures and test-only extensions—never real sessions, credentials, or production state.

The workspace contains trusted in-process contributions and explicitly configured child-process adapters. A crate under plugins/ signals architectural role; it does not imply dynamic loading, sandboxing, or a stable third-party ABI. Follow the existing registry, manifest, and protocol for the extension type.

Adding a provider

  1. Choose crates/plugins/harnesses/, capabilities/, or connectors/. Shared machinery belongs in plugins/host/; provider parsing stays with its provider.
  2. Depend on the narrowest kernel, protocol, or extension API. Keep storage authority and capture policy host-owned.
  3. Use the existing in-process registry or the explicit process manifest/protocol. Do not add provider-specific branches to generic host code.
  4. Add synthetic contract and lifecycle tests. Shared golden inputs go in crates/test-support/fixtures/.
  5. Run cargo fmt --all -- --check, cargo clippy --workspace --all-targets --locked -- -D warnings, and cargo test --workspace --locked from the root.

Workspace packages share Rust 2024, resolver 3, toolchain, and license metadata. Crate versions remain local because executable and internal contract release cycles can differ.

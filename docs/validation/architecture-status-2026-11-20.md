## Current architecture through PR #295

- **Harness adapters and UI contributions.** Trusted adapter declarations now own Kiro collector status, Codex state context and generic native reader status. Opt-in Rust Pi user-text and requested-command modes pass exact source references through host admission; normal capture remains metadata-only. Trusted Activity providers show short-lived, explicit `z` previews. PR #262 adds a requested-shell-command preview: bounded redacted text stays in inspector state, expires after 20 seconds, is rechecked, and does not enter Activity rows, copy, Review or export. A requested command does not prove execution or success. PR #270 moves Kiro permission fields and details into a trusted session-inspector provider; a synthetic provider uses the same bounded shell without a new pane or duplicate built-in labels. PR #271 puts capture-mode config and session startup behind a host-owned registry, while Pi's exact reference admission remains source-specific. A TOML file or child process cannot register a host validator. See the [preview](pi-command-activity-preview.md), [inspector](kiro-inspector-contribution.md) and [capture-registry](capture-mode-registry-phase1.md) checkpoints.
- **Private-reference proof.** PR #291 adds a test-only separately executed synthetic child and proves the bounded path from a reference payload containing only its digest and event metadata through host byte/fingerprint proof, trusted admission, Activity projection, exact read, redaction, revoke and fingerprint reset. The child can access the configured test-root path supplied by the fixture; it does not send source bytes over the protocol. This enables no production capture mode or real harness provider. See the [end-to-end fixture checkpoint](trusted-private-reference-e2e.md).
- **Cooperating writer lease (PR #293).** The telemetry `Store` can opt into a Linux-only, feature-off-by-default sibling lock before constructor mutations. It binds the lock to the database path and file identity, shares ownership among same-process Stores, and retains the lock until known readers/workers quiesce on close or constructor failure. This is a cooperative gate for participating telemetry Stores only: it does not exclude legacy binaries or already-open SQLite handles, cannot detect an in-flight swap-and-swap-back, and does not cover WorkflowStore, TaskStore, direct SQLite routes or outbound actions. Python remains the production writer; this does not establish cutover safety. See the [lease checkpoint](python-store-cooperating-writer-lease.md).
- **Rust scratch source activation (PR #295).** The typed v2 `ActivateSource` operation handles only an explicitly marked scratch database. It uses explicit safe defaults, renews only the lease for a supported active metadata-only source, preserves cursor/policy/dirty state, checks both current content receipts for nonempty cursors, and persists typed replay receipts with bidirectional request-ID checks across activation/admission/revocation. It rejects revoked, private, unsupported and orphan state. This does not route production calls or replace Python `Store`. Independent exact-head review cleared the implementation; all 14 GitHub checks were queued at merge. See the [activation checkpoint](rust-v2-scratch-source-activate.md).
- **Rust storage boundary.** The Linux service is feature-off. Its default mode still serves only a v1 probe; an explicit experimental v2 mode writes lifecycle evidence to one fixed, pre-existing, marked **disposable scratch database** under a distinct service UID. It never opens the canonical receiver database. PR #263 proves separate service/client identities, peer rejection and fresh Python `Store` denial against a private data root, but cannot revoke an already-open old handle. PR #264 defines strict typed 64 KiB v2 requests/replies; #267 bridges them into the guarded scratch transaction with an atomic replay receipt; #269 tests service dispatch, private sidecars and lost-reply retry under separate UIDs; #272 adds a Rust client that verifies the service peer before sending lifecycle bytes and validates the request-bound reply. The scratch service's lease, policy and digest fields remain tied only to its disposable fixture, not to production Store authority. See the [account](rust-storage-distinct-principals.md), [contract](rust-storage-mutation-v2.md), [bridge](rust-v2-scratch-bridge.md), [service](rust-service-v2-scratch-dispatch.md) and [client](rust-v2-client-contract.md) checkpoints.
- **Writer cutover gates.** Python `Store` remains the production canonical writer. The write inventory includes Store initialization, migration, derived repair, OTLP, retention, plugin admission/projection and receiver policy; separate `WorkflowStore` and `TaskStore` databases; native lifecycle outbox writes; and outbound delivery. PR #265 adds a fail-closed read-pool drain result, and #268 adds an explicit feature-off handoff check for one Store's known connections and workers. Neither proves all Python writers have stopped. Outbound dispatch holds a separate flock and can perform an external action **between** Store connections; dispatch/reconciliation and uncertain outcomes need their own quiescence proof. A point-in-time authority marker and cooperating lock cannot exclude old processes with already-open writable SQLite handles. Before Rust authority, route every durable mutation through a service API, prove all writers/leases quiescent, use a protected versioned canonical path under a distinct service identity, and test supported old binaries against both canonical and archived paths. Migration needs a consistent backup including WAL, receiver identity and receipt verification, plus forward recovery after the first Rust durable write. Explicit/shared stores and other platforms need separate qualification. See [read-pool](read-lease-quiescence.md), [Store handoff](store-handoff-quiescence.md) and [writer ownership](rust-writer-cutover-gate.md) checkpoints.
- **Verification state.** Focused, independent checks passed for the relevant slices: #262's final 30 UI/route tests and two live checks; #263's two-UID Docker proof and ten installed service tests; #264's 17 Rust contract tests and one Python differential; #265's 19 read-pool tests; #267's 25 Rust and 13 installed scratch tests; #268's 28 Store/read-pool tests; #269's 27 Rust, 23 installed and two Docker fixtures; #270's 31 final UI tests and independent collision/layout checks; #271's 100 independent plugin tests and 21 installed Pi tests; #272's 23 Rust tests and two-UID Docker fixture; and #293's 19 lease tests plus 28 Store/read/auxiliary handoff tests. #293 also passed compile checks and documentation link checks. #266 changed documentation only. Rust formatting and Clippy passed on affected Rust slices. All 14 GitHub checks for #293 were **queued at merge**; those local results are not a completed CI matrix. PR #295 passed workspace formatting and Clippy, 150 Rust workspace tests, 15 installed scratch tests and 10 installed service tests locally. All 14 GitHub checks were queued at merge, so CI completion is not established by this local evidence. No whole-app Rust performance gain or production Rust writer cutover is claimed.

An independent Rust architecture review found the crate dependency direction clean: the host depends on the protocol, harness binaries depend on shared source crates, and the domain reducer and exact-query crate have no harness dependency. It found no merged Rust path writing directly to Agenturm's Store. Bounded multi-session paths now exist for opt-in Codex and Pi directory readers through the shared source crate, with Store-owned member ownership, conservative root/member continuity disposition and a visible source availability overlay. The next correctness gates are complete evidence and content-backed Review parity for one real harness, remaining source-history limits, and full live query/storage compatibility. Remaining Python compatibility logic should leave generic services through registered contributions.

Python remains the sole writer until source semantics, query compatibility, crash recovery and rollback gates pass. The user chose idiomatic Rust for the implementation; performance is measured separately and is not a prerequisite to continuing the architecture work.

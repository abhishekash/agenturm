Rust activation on a real Store clone

20 November 2026 · feature off · Linux

A separate service principal activates metadata-only sources on a detached copy of an actual Python Store database. Python remains the production writer.

Authority has not changed. The service does not accept a database path from a client or connect to Agenturm's receiver. The clone marker is not in a normal production database.

Service boundary

  • Fixed telemetry-clone.db in a service-owned private root, pinned inode, bounded sidecars and a durable writer lock.
  • Explicit clone marker plus real Store authority and read-schema markers; peer-checked v2 Unix socket with distinct client and service identities.
  • Only ActivateSource: transactional receiver, generation, capture and history checks; fresh lease epoch; cursor and policy preserved; request-bound replay receipt.
  • Private-reference ownership and unsupported source history fail closed.

Validation

A two-UID fixture uses real Store backups, compares Rust and Python activation fields, checks lost-reply replay, restart, wrong peer/receiver, conflicting generation, revoked and private-reference sources, unsupported operation, same-byte replacement inode and unchanged original data. Rust suites run separately. GitHub CI results are not implied by local checks.

Cutover remains open

The explicit marker and path are a test boundary, not a proof that an operator could never place canonical data there. Production activation, batch admission, private reference handling, other stores and outbound mutations, old held-open writer exclusion, synchronized migration, publication and forward recovery remain required.

See the writer cutover gate and Markdown record.

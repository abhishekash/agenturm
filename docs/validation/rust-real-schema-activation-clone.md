# Rust lifecycle operations against a detached real Store clone

20 November 2026. This is a feature-off Linux storage-service slice. Python `Store` remains the production writer. The service accepts no canonical database path from a request and does not start from the receiver.

## Boundary

`--experimental-real-clone-activation enabled` requires one service-owned `0700` data root containing a fixed `telemetry-clone.db` and only its known SQLite sidecars and private writer lock. The file must be a singly linked `0600` regular file with `schema_meta.storage_activation_clone_v1=enabled`, `storage_authority_v1=python-v1`, and `plugin_sessions_read_schema=1`. The marker is added only to a detached test clone; it is absent from ordinary production databases. A distinct client UID/GID connects through the existing peer-checked Unix socket. A v2 frame contains no database path. The service pins the clone inode, verifies it across requests, and enforces a private umask.

Only `ActivateSource` and `AdmitLifecycle` are accepted. Activation and batch admission use separate `BEGIN IMMEDIATE` transactions. Rust checks receiver identity, source ownership, artifact generation, active capture policy and supported metadata-only history. Admission atomically updates the source cursor, evidence rows, dirty sequence, empty-reference receipt/status and a request-bound replay receipt. Exact retry remains idempotent after a lost reply or service restart; reusing a request ID for different bytes is rejected. The cursor and replay receipt are committed with the evidence before the caller may acknowledge the batch.

The admitted batch is intentionally narrow: at most 48 canonical lifecycle facts with revision zero and bounded IDs/payloads. Discovery members, root/member gaps, corrections, messages/tools/checks, private references, retention, and capture-policy changes remain unsupported. The service rejects revoked sources, stale leases/cursors, private content fingerprints, recorded reference providers, and other unsupported source history. Python's reference-provider ownership behavior remains a separate parity gate; the differential compares core source/cursor/evidence/dirty/content-receipt state and does not claim provider-table parity. The v2 storage cursor bound is 800 UTF-8 bytes, matching the shared Rust/Python process-source contract. A request cannot select a database path, run a migration, publish a canonical path, or activate a production writer.

## Evidence and remaining gates

The disposable two-UID fixture creates a real Python `Store`, makes independent SQLite backups, activates through Rust, and compares a typed Rust lifecycle batch with Python `commit_batch` on the oracle copy. Rust contract tests check the 800-byte cursor limit; the fixture also sends an exact 800-byte cursor through the service and verifies the stored value and reply. It checks malformed content batch and status receipts are refused without mutation, trigger rejection with no partial cursor/evidence/receipt, lost reply followed by exact replay, restart/WAL replay, source revocation followed by stale-lease rejection, rejected private-fingerprint/private-owner sources, core evidence/cursor/dirty/content-receipt parity, unchanged canonical files, and the original activation checks. Activation and lifecycle admission reject persistent and TEMP triggers on their write tables before mutation. Admission shares activation's full active-source history gate and rechecks the receiver, source lease and capture fields, and request receipt namespace before commit. Rust regressions cover attempted receiver, lease, capture, sibling-source and receipt changes. The Rust storage service, contract, and admission suites run separately. GitHub CI is a separate gate and must not be inferred from local results.

The marker and fixed private path constrain this opt-in fixture; they do not prove that a future operator cannot place a canonical database there. No production client routes activation or admission to Rust. The service does not provide full Python reference-provider parity, revisions, discovery/gap handling, capture policy, or migrations for WorkflowStore, TaskStore or outbound state. Other live Store instances, older held-open writers, coordinated backup publication, full write-route parity and forward-only recovery remain cutover gates. See the [writer cutover gate](rust-writer-cutover-gate.md).

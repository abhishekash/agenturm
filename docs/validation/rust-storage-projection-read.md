# Rust backup-only session projection read

Recorded 20 November 2026. This checkpoint extends the diagnostic `agenturm-storage-shadow` reader to read one source's published session projection from an explicitly supplied **isolated SQLite backup**. It does not read the live Store, publish a query, write a database, or change Python's authority. The default revision-certificate request and response remain byte-compatible; callers opt into the additional `sessions` field with `"include_projection": true`.

## Snapshot and validation contract

The Rust reader opens the backup with SQLite `READ_ONLY`, URI `immutable=1` and `query_only`, rejects sidecars, and reads the receiver/source revision and its projection rows inside one short read transaction. It returns sessions only when capture is enabled and the source's projected sequence and policy equal its dirty sequence and policy. Unknown, pending and disabled sources have no `sessions` field. The receiver/source/lease/policy/dirty certificate remains historical: a caller must still use Python's live `rust_shadow_snapshot.current()` fence before publishing any result.

The source is matched by exact ID. SQLite checks a maximum of 2,001 rows and the byte lengths of stored text **before Rust loads those strings**; more than 2,000 rows, more than 4 MiB of aggregate stored text, a usage field over 4 KiB, or an oversized identity/relationship field fails closed. Each row's policy and dirty sequence must match the same ready certificate. Rust validates typed IDs, states, reason/relationship fields and nonnegative timestamps, then recomputes the Python `plugin:<sha256>` session key from receiver, source and native session ID. It returns the same normalized session fields as Python's read-only shadow snapshot, including reported/run state and partial relationship metadata. It does not re-reduce evidence.

Usage counters use `serde_json`'s raw-number view, which preserves the decimal token without floating-point conversion. The receiver admits at most 50,000 records per source and each usage observation is at most `i64::MAX`; therefore one stored aggregate cannot exceed `50,000 × i64::MAX`. Rust parses that entire valid range as `u128`, rejects negatives, fractions, exponents, duplicate or unknown counter keys, and emits values through `2^53−1` as JSON numbers and larger values as decimal strings, matching Python's API-safe conversion. This adds only `raw_value` support to `serde_json`, not workspace-wide arbitrary-precision Number parsing.

## Verification and limits

Installed differential tests compare the full Rust rows to Python `rust_shadow_snapshot.capture(...).expected["sessions"]` for two sessions, a parent relationship, mixed lifecycle states, the JSON-safe boundary and a sum beyond `u64`. They compare source-gap `unknown`/`source_gap` rows, require no rows while projection is pending or capture is disabled, and prove that a formerly ready backup remains historical after Python's live fence rejects it. Corrupt policy/dirty revisions, session key, native identity, relationship, time and usage JSON fail closed. The test also checks that default v1 response bytes match an explicit `include_projection: false` request and that the isolated backup and its sidecar set do not change.

Focused gate: `cargo test -p agenturm-storage-shadow`, `cargo clippy -p agenturm-storage-shadow --all-targets -- -D warnings`, and six installed `tests.test_rust_storage_shadow` tests. The supplied file must be a completed, quiescent backup. `immutable=1` and the sidecar check do not prove that another process is not changing it. Live query parity, a Rust writer, exactly-one-writer cutover, downgrade handling and crash/rollback drills remain open; no performance gain is claimed.

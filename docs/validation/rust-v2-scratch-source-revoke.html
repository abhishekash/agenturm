Rust v2 scratch source revocation

Experimental · scratch only · 20 November 2026

This policy operation does not change production capture policy, the canonical receiver database, or Python Store authority.

Contract and transaction

The typed RevokeSource request carries the current source lease, acknowledged cursor, and expected dirty sequence. Under BEGIN IMMEDIATE, the service checks the receiver, explicit scratch marker, pinned path, writer lease, and exact source lease.

Revocation increments lease and policy epochs, disables capture, clears the content fingerprint, advances the dirty sequence, and retains the acknowledged cursor. It removes lifecycle evidence and related projection, Activity, content-status, and dirty rows in the same transaction.

Requests fail before mutation when private-reference ownership, stored content, member state, continuity gaps, retention, or non-lifecycle evidence exist. Rust has no trusted reference-provider cleanup SPI, so the operation refuses private-provider history.

The durable request receipt makes exact retries safe across database reopen. Changed bytes or reuse of the ID by the other v2 operation fail closed; admission and revocation check both receipt namespaces.

Validation

Local Rust checks passed: 42 tests (24 contract, 16 scratch-admission, 2 Linux service), workspace formatting, and Clippy with warnings denied. The installed Python scratch-admission module passed 14 tests, including a real Store-backed case for projection cleanup, epoch fencing, stale admission denial, retry in a second process, changed-request rejection, and cross-operation request-ID conflict.

This remains unavailable to canonical database callers. Python Store remains the production writer and capture-policy authority. Writer exclusion, migration, recovery, compatibility, and platform gates remain open. No performance gain is claimed.

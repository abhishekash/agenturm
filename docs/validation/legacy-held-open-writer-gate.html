Held-open legacy writer

20 November 2026 · Linux two-UID negative gate · feature off

An old Python Store can keep writing to an archived SQLite inode after its pathname and ownership change.

No Rust writer authority was enabled. The current service supports an empty probe root or explicit scratch database, not a migrated canonical Store.

Observed result

  1. A legacy-identity Store committed a WAL row and kept its SQLite handle open. A detached backup preserved the row and receiver identity in a service-only directory.
  2. After the old connection began a transaction, the fixture moved and changed ownership of the old main file and WAL/SHM sidecars. The held connection still committed a new row, DDL, and a second receiver identity to the archive.
  3. Fresh old Store and direct SQLite opens of the candidate and archive were denied. The protected candidate retained its original bytes, row and receiver identity.

Reproduce

Use an isolated Linux VM or the existing Docker image. The script creates no system accounts and touches only its disposable temporary tree.

docker run --rm --network none --read-only --tmpfs /tmp:rw,exec,size=128m \
  -v "$PWD":/src:ro -w /src python:3.12.15-slim-bookworm \
  python scripts/validate_legacy_held_open_writer.py

The local Docker run passed. The Rust CI job runs the same fixture with sudo; its GitHub result is pending.

Cutover gate

This is a test-only protected candidate. The current Store stands in for an older wheel; supported old releases and the actual published path still need adversarial tests. Writer discovery and drain must happen before backup and archive. Multi-store consistency, production publication, platform ACLs, and forward recovery remain open.

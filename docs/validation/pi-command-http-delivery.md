# Exact Pi requested-command HTTP delivery

Recorded 20 November 2026. `GET /api/plugin-command-content?event_id=...` delivers one transient, redacted **requested shell command** for an opt-in Pi Activity item. A started shell fact means Pi recorded a command request. It does not prove the command executed or succeeded. Metadata-only remains the default capture mode. This route does not add command content to Review, Activity rows, copy, export, or a generic raw API.

The route inherits the receiver's bearer token and Host/Origin checks. It additionally requires both the bound receiver and client to be loopback addresses, even when receiver authentication is explicitly disabled. It accepts exactly one canonical plugin Activity event ID. The trusted `read_exact_pi_requested_command` gate binds that ID to the active Pi source, enabled grant, current projection, Store, exact started shell fact, source row, and nofollow member proof. Unavailable evidence returns only a generic 404.

The response contains `receiver_id`, `event_id`, `redacted_text`, `clipped`, and `[lease_epoch, policy_epoch, source_dirty_seq]` as `revision`. The text is sanitized again and limited to 4,096 UTF-8 bytes. The route records the Store and Activity source file identities, disables response caching, and reruns the full read gate and identity checks immediately before HTTP headers. A change during that interval yields 409 without command text. Every response uses `Cache-Control: no-store`.

Focused validation: `python -m unittest tests.test_plugin_command_content_delivery tests.test_plugin_pi_command_read tests.test_plugin_content_delivery -q` with the installed project environment. The HTTP tests cover authorization, Host, no-auth loopback enforcement, invalid and duplicate IDs, redaction and size, uncached repeated reads, revocation, source rewrite, Store replacement before and at the header boundary, and receiver change at the header boundary. This is correctness coverage, not a performance claim.

Rust scratch storage admission

A feature-off transaction experiment for one host-prepared lifecycle batch. Python remains Agenturm’s production database writer.

Boundary

  • The standalone crate is absent from the receiver, plugin host, wheel, and Python Store runtime.
  • A disposable, existing regular SQLite file must carry schema_meta.storage_admission_scratch_v1=enabled. The marker is checked before and inside the write transaction.
  • The caller supplies host-prepared canonical metadata and lease values. The crate does not parse plugin frames, compute hashes, sanitize arbitrary child payloads, or grant child storage access.
  • Only up to 48 revision-zero lifecycle facts from a metadata-only source without discovery, content, gaps, retention invalidation, or other evidence are supported.

Transaction

Inside BEGIN IMMEDIATE, the scratch writer checks receiver, source, plugin, generation, lease, policy and capture state. Evidence, cursor, batch digest, dirty marker and empty-content receipt/status commit together. Exact replay and unchanged idle polls leave the fixture unchanged. Stale, conflicting or unsupported input rolls back.

Verification

Installed differential tests compare a disposable Rust-written Store fixture with Python commit_batch for the supported lifecycle path, including persisted rows, replay and idle. Separate tests cover rollback, stale lease/cursor, revoked capture, missing scratch marker and unsupported corrections. The crate also has in-memory Rust unit tests.

Still open

This does not cover full admission policy, content, source gaps, retention, corrections, one-writer exclusion, legacy-writer fencing, physical backup/WAL handling or safe cutover. No performance gain is asserted.

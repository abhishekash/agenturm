Agenturm kernel architecture checkpoint

Updated 20 November 2026 at merged main 2018225 (including PRs #262–#291). This is an implementation checkpoint for the reviewed Rust kernel plan, not a completed migration or a speed claim. The table below preserves the earlier PR #234 snapshot; the current changes and gates are recorded first. The execution ledger lists the intervening PRs through #291.

Current architecture through PR #291

  • Harness adapters and UI contributions. Trusted adapter declarations now own Kiro collector status, Codex state context and generic native reader status. Opt-in Rust Pi user-text and requested-command modes pass exact source references through host admission; normal capture remains metadata-only. Trusted Activity providers show short-lived, explicit z previews. PR #262 adds a requested-shell-command preview: bounded redacted text stays in inspector state, expires after 20 seconds, is rechecked, and does not enter Activity rows, copy, Review or export. A requested command does not prove execution or success. PR #270 moves Kiro permission fields and details into a trusted session-inspector provider; a synthetic provider uses the same bounded shell without a new pane or duplicate built-in labels. PR #271 puts capture-mode config and session startup behind a host-owned registry, while Pi's exact reference admission remains source-specific. A TOML file or child process cannot register a host validator. See the preview, inspector and capture-registry checkpoints.
  • Private-reference proof. PR #291 adds a test-only separately executed synthetic child. Its protocol payload carries only a digest and event metadata; the child can access the configured test-root path supplied by the fixture. The host proves source bytes and fingerprint, trusted admission commits provider ownership, Activity projection permits an exact read, and revoke/fingerprint reset fail closed. No production capture mode or real harness provider is added. See the end-to-end fixture checkpoint.
  • Rust storage boundary. The Linux service is feature-off. Its default mode still serves only a v1 probe; an explicit experimental v2 mode writes lifecycle evidence to one fixed, pre-existing, marked disposable scratch database under a distinct service UID. It never opens the canonical receiver database. PR #263 proves separate service/client identities, peer rejection and fresh Python Store denial against a private data root, but cannot revoke an already-open old handle. PR #264 defines strict typed 64 KiB v2 requests/replies; #267 bridges them into the guarded scratch transaction with an atomic replay receipt; #269 tests service dispatch, private sidecars and lost-reply retry under separate UIDs; #272 adds a Rust client that verifies the service peer before sending lifecycle bytes and validates the request-bound reply. The scratch service's lease, policy and digest fields remain tied only to its disposable fixture, not to production Store authority. See the account, contract, bridge, service and client checkpoints.
  • Writer cutover gates. Python Store remains the production canonical writer. The write inventory includes Store initialization, migration, derived repair, OTLP, retention, plugin admission/projection and receiver policy; separate WorkflowStore and TaskStore databases; native lifecycle outbox writes; and outbound delivery. PR #265 adds a fail-closed read-pool drain result, and #268 adds an explicit feature-off handoff check for one Store's known connections and workers. Neither proves all Python writers have stopped. Outbound dispatch holds a separate flock and can perform an external action between Store connections; dispatch/reconciliation and uncertain outcomes need their own quiescence proof. A point-in-time authority marker and cooperating lock cannot exclude old processes with already-open writable SQLite handles. Before Rust authority, route every durable mutation through a service API, prove all writers/leases quiescent, use a protected versioned canonical path under a distinct service identity, and test supported old binaries against both canonical and archived paths. Migration needs a consistent backup including WAL, receiver identity and receipt verification, plus forward recovery after the first Rust durable write. Explicit/shared stores and other platforms need separate qualification. See read-pool, Store handoff and writer ownership checkpoints.
  • Verification state. Focused, independent checks passed for the relevant slices: #262's final 30 UI/route tests and two live checks; #263's two-UID Docker proof and ten installed service tests; #264's 17 Rust contract tests and one Python differential; #265's 19 read-pool tests; #267's 25 Rust and 13 installed scratch tests; #268's 28 Store/read-pool tests; #269's 27 Rust, 23 installed and two Docker fixtures; #270's 31 final UI tests and independent collision/layout checks; #271's 100 independent plugin tests and 21 installed Pi tests; and #272's 23 Rust tests and two-UID Docker fixture. #266 changed documentation only. Rust formatting and Clippy passed on affected Rust slices. Each #262–#272 PR had 14 GitHub checks queued at merge; those local results are not a completed CI matrix. No whole-app Rust performance gain or production Rust writer cutover is claimed.

Historical snapshot through PR #234

Harness adapters Trusted bundled native readers register source, format and turn Review contributions. Opt-in Rust Pi, Codex, Claude Code, Kiro and OpenCode process readers use framed supervision, Store admission, durable cursors and explicit source replacement. Opt-in Codex and Pi directory modes can each track up to 48 JSONL files through one process with atomic member checkpoints, a four-file poll budget and fair scan progress. Their discovery and checkpoint engine lives in the reusable Rust agenturm-directory-source crate; each supplies its own JSONL format and stable diagnostic namespace, and a synthetic format also exercises the engine. A failed root enumeration commits a source-wide d2 gap; a previously acknowledged unreadable file commits a d3 member gap while retaining its checkpoint for recovery. An acknowledged member removal commits a scoped tombstone: same-path reappearance with the old native identity and a worker restart leave that session Unknown/source_gap, while a healthy sibling stays current and a genuinely new identity can establish a new session. Exact member ownership preserves healthy siblings, while legacy or ambiguous ownership falls back to source-wide invalidation. Pi process tool results recover their original turn only from one retained policy-current call with a strictly earlier source timestamp; ambiguous links remain partial. Shared JSONL replacement-gap diagnostics now replay identically across mtime-only changes, and acknowledged prefixes are verified. OpenCode's oc2 cursor catches same-count row replacement and ordinary restored-mtime rewrites. A feature-off Pi directory content gate can admit bounded, redacted user-message text only after the receiver reopens its member, proves the exact row and a host-derived initial generation, and commits content with metadata and cursor. Pi and Codex directory discovery are explicit opt-ins; Pi single-file mode remains the default. Switching Pi modes under one durable source ID fails visibly, so each mode needs a distinct source ID. Other harnesses still need their own format binding and installed rollout gate. Process readers still need broader native-format and content-backed Review/export parity before default replacement. The Pi content gate has no process wire/configuration or API/TUI/export reader; normal capture stays metadata-only. Post-gap generations are withheld until a host-owned anchor exists. Deletion and recreation entirely between two polls can still be invisible when the acknowledged path and prefix are restored; an observed removal stays gapped. Changed replacement bytes or identity between retries need separate continuity treatment. Full-prefix JSONL verification can read up to 1 GiB per idle poll at the 512 MiB ceiling; whole-app cost has not been measured.

App-mediated Ctrl+C paths check the same policy. Capability process activation remains opt-in and UI models refresh asynchronously. Prompt signals and Action observations report observations rather than efficacy or causality. New fact domains, general third-party SDK guarantees and broader metric capabilities remain open. The scope registry does not grant process plugins native capture authority. Full Pi content Review/export parity remains open; a source may change between the last export proof and local file creation, and text already displayed cannot be retracted from terminal-level selection.
Rust host and distribution The opt-in Rust process host runs installed adapters under Python Store and policy authority. Control writes, backpressure, bounded discovery and process-group cleanup have regression coverage. A Linux x86_64 wheel bundles a SHA-pinned host and passes isolated installed receiver checks; the pure wheel remains functional. Further platform wheels, publication gates, default activation and a measured whole-app performance result remain.
Durable authority Python Store owns capture policy, leases, admission, global and member cursor/commit/ack, session-member ownership, retention, projection and the sole database writer. Root and member read gaps commit with their cursors and invalidation before acknowledgment. Native capture-scope migration reads its marker after taking SQLite's writer lock and replaces owner-clearing triggers transactionally. A read-only Rust shadow snapshot is fenced by receiver, lease, policy, dirty sequence and published revision. A separate backup-only Rust SQLite inspector reads the same receiver/source revision and, when requested, up to 2,000 policy-current session projection rows from a caller-supplied isolated backup with read-only, immutable and query-only settings. It bounds stored text before loading and validates identity, session key, state, relationship, time and usage fields against the same source revision. An optional strict v1 Activity read validates up to 50,000 content-free published rows, source ownership, fixed action vocabulary and exact field allowlists in that same backup transaction; it does not re-reduce evidence. Both outputs carry a historical certificate, and Python must still check live freshness. Pure Rust reducer fixtures v1–v3 match Python lifecycle, usage, relationship, current v3 Activity and durable source-gap invalidation on the tested corpus. Pure Rust exact-session and exact-Activity queries check source scope and always report partial coverage over a validated v3 snapshot. An opt-in backup-only Rust exact query selects one validated published session or Activity row and returns partial historical coverage. It requires a trusted isolated backup. An opt-in Python diagnostic attester compares the row or exact absence with a fresh policy-current Store projection, checks receiver/revision and Store file identity, then calls current() before returning the Python row. The Rust backup query and storage inspector cannot themselves check live freshness. The Python attester is point-in-time, and no production query route uses it. New Activity projection fields need an explicit versioned compatibility decision. Full live query/storage compatibility, Rust authority, legacy writer exclusion, one-writer cutover and rollback drill remain. No production data is written by Rust storage.

The new boundaries are documented in backup exact query, live exact attestation, and the Pi content reference gate.

An independent Rust architecture review found the crate dependency direction clean: the host depends on the protocol, harness binaries depend on shared source crates, and the domain reducer and exact-query crate have no harness dependency. It found no merged Rust path writing directly to Agenturm's Store. Bounded multi-session paths now exist for opt-in Codex and Pi directory readers through the shared source crate, with Store-owned member ownership, conservative root/member continuity disposition and a visible source availability overlay. The next correctness gates are complete evidence and content-backed Review parity for one real harness, remaining source-history limits, and full live query/storage compatibility. Remaining Python compatibility logic should leave generic services through registered contributions.

Python remains the sole writer until source semantics, query compatibility, crash recovery and rollback gates pass. The user chose idiomatic Rust for the implementation; performance is measured separately and is not a prerequisite to continuing the architecture work.

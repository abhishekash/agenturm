The unprofiled active run sampled /api/sessions p95 at 11.4 ms, /api/activity?limit=50 at 12.7 ms, /api/mcp?limit=20 at 33.4 ms, and /api/health at 40.7 ms. The sample count is small and does not establish the plan's 120-second or 200-request latency gates. The active profiler's SQLite execute self-time was about 0.91–1.10 seconds per receiver segment, while JSON raw_decode was about 0.02–0.05 seconds; this is directional attribution only, not a controlled end-to-end Rust speedup estimate. Cockpit selector/style work was also prominent. The profiling exit failure disappeared in the unprofiled comparison, but one comparison does not prove its root cause.

Decision: A Rust JSON parser is not justified as the first production performance slice by this evidence. Keep Python as the only storage authority. Inspect native SQL/transaction behavior and cockpit refresh/styling with representative retained history, then select a bounded Rust component only if a measured compute hotspot and whole-monitor gain are demonstrated.

The host had about 1.6 GiB free during the idle run. The retained-history acceptance fixture requires a 4 GiB reserve plus headroom, so that gate was not run here. The generated runs used a 1 GiB reserve. The previously measured clean unprofiled 300-second generated idle run was 7.10% of one core, above the plan's under-5% retained-history target; it cannot be relabeled as a pass.

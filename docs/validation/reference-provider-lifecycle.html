Trusted reference provider lifecycle

20 November 2026 · trusted extension

Reference providers install their schema and erase their source rows through host-owned transactions. Python Store remains the production writer.

Authority has not changed. TOML and child processes cannot install a provider. Older binaries do not honor these hooks or the provider ownership table.

Host contract

  • The bundled Pi providers initialize at Store startup. An explicitly supplied trusted registry installs before a process session activates; failed DDL rolls back.
  • The host records every installed provider whose commit hook ran, including unselected providers. Ownership remains recorded even if its rows later become empty. Older Pi rows are adopted on database open.
  • Capture revocation or fingerprint change requires every recorded provider, then erases its rows in the same transaction as host policy changes. Missing or failed hooks roll back the change.
  • A second Store without a custom provider refuses cleanup. The default registry cannot silently leave private provider rows behind.

Validation

Focused tests cover schema rollback, atomic source erasure, missing-provider denial, fingerprint reset, stale lease fencing, and legacy Pi status adoption. A synthetic nonprivate audit provider proves its receipt is erased on revocation.

Remaining limits

The process wire still carries Pi-specific content and command references. A new private-content harness needs its own bounded wire contract, source proof, read gate, and end-to-end revocation test. This lifecycle hook does not prove exclusion of older writers or a Rust production cutover.

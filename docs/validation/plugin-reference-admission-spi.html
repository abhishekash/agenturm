Architecture checkpoint

Trusted reference admission

A receiver-owned provider registry now handles the reference portion of commit_batch. Existing Pi proof moves behind provider hooks while the receiver keeps the evidence and cursor transaction.

Authority and transaction

1 Select and bind

The trusted capture mode names a registered provider. The child supplies bounded references only. The provider validates their exact shape and binds the host grant to the source lease.

2 Prove source

The receiver checks the lease and member checkpoint. Pi providers then reopen and prove exact configured source bytes outside the SQLite writer transaction. Mutable content refs are snapshotted first.

3 Recheck and commit

Within one writer transaction, the receiver rechecks receiver identity, lease, policy, fingerprint, cursor, and member checkpoint. Evidence, dirty marker, provider rows, and receipts commit together.

4 Replay exactly

Every installed provider checks its receipt on replay. A previously acknowledged cursor cannot acquire or change reference content. Provider failure rolls back the whole transaction.

What is implemented

Pi user text and command source proof, redaction, pruning, statuses, and receipts are Pi-owned. The Pi content provider preserves the shared unanchored_origin diagnostic for Pi commands without accepting unrelated provider reasons. Legacy direct-call arguments resolve through the same providers. A synthetic trusted audit provider proves atomic dispatch without private content.

Remaining gates

This does not enable arbitrary third-party private content capture. Schema setup, revocation and configuration cleanup, and process wire families still have Pi-specific paths. The synthetic nonprivate receipt survives revocation while metadata is erased and the lease is fenced; private providers need lifecycle cleanup first.

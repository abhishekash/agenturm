# Process source-gap invalidation checkpoint

Recorded 20 November 2026. The receiver now treats a process adapter's `possible_source_gap` diagnostic as an explicit loss of continuity for sessions already admitted from that source. The Python Store remains the sole writer and policy authority. A diagnostic still cannot prove that a source change happened; it reports that prior evidence may be incomplete.

When the host admits a new, source-wide gap diagnostic, it captures the native session IDs already seen from that source in the **same transaction** as the evidence batch, durable cursor, and dirty sequence. The next policy-current projection marks those sessions `unknown` with `source_gap`, removes their usage total and confirmed parent relationship, and suppresses their content-free Activity. A distinct session first observed after the gap may project normally. A later gap captures sessions that were new after the first. The invalidation survives restart and exact batch replay; capture revocation erases it with the source's evidence. A gap diagnostic must be a new revision-zero, source-wide fact; a correction or session-scoped diagnostic fails before cursor acknowledgment.

The receiver caps the combined retained, invalidated, and incoming native session IDs at 2,000. If it cannot record every affected session, the whole batch fails before the cursor advances. A source-gap diagnostic is exempt from the old occurrence-time retention horizon because its timestamp may be zero; ordinary evidence remains fenced. Existing databases with gap diagnostics admitted before this change have no durable record of which sessions preceded each gap. On first migration, those sources are conservatively marked source-wide `source_gap` until capture is explicitly reset. This can also mark sessions observed after an old gap Unknown; it avoids presenting a stale Completed state as certain.

Focused tests cover a completed session becoming Unknown after a gap, erased usage and relationship, hidden Activity, a distinct new session after the gap, a second gap, same-batch ordering, replay and restart, capacity rollback, capture revocation, receiver HTTP health, retention interaction, and conservative migration. Seven new tests passed. Ninety-three existing plugin tests passed locally, with 28 Rust installed tests skipped until their binary environment variables were supplied; all 28 then passed against the installed Pi, Codex, Claude Code, and Kiro binaries. The older Pi and Codex rewrite assertions now require Unknown/source_gap instead of trusting a terminal fact from a previous generation. The mechanism responds only to a detected and admitted gap. It cannot discover source changes that an adapter does not detect, retract a particular deleted SQLite row without a gap signal, or reconstruct missing evidence. No performance claim is made.

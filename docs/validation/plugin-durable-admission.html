Durable plugin admission checkpoint

19 November 2026 · Opt-in process adapter inbox. The Python Store remains the sole database writer.

Three Store tables retain source ownership and cursor, canonical metadata evidence, and a dirty sequence for later projection. One SQLite transaction admits every record, advances the cursor and updates the dirty marker. A conflict rolls back the whole batch. The process host sends an acknowledgment only after the Store returns the accepted cursor.

Activation issues a new lease and preserves the cursor for the same source, plugin and exact artifact hash. A stale worker cannot write. After a crash between commit and acknowledgment, an exact replay returns the committed cursor without duplicate evidence. A different batch at that cursor is rejected.

This receiver-owned fence is not an OS sandbox or a credential for same-process code. The inbox is not connected to production collection or live UI projection.

The inbox admits coarse lifecycle state and reason code, nonnegative token counters, and diagnostic code/severity. It rejects message, tool and relationship records and arbitrary prompts, paths and output. The wire schema remains provisional; production activation, policy-epoch reconciliation, connector, public SDK and Rust storage authority are later gates.

Validation: 16 process/admission tests passed locally. They cover a real executable fixture, acknowledgment ordering, restart replay, source conflict, stale lease, changed revision, rollback, malformed metadata and timestamps above JavaScript’s exact integer range.

Receiver-owned SPI

Trusted private Activity read-provider checkpoint

The receiver uses a bounded, immutable ReferenceReadRegistry for explicit private-content previews. Trusted host code installs each reader. The host checks the exact Activity event, durable source ownership, receiver identity, capture enablement, current policy and lease, and projected source revision before and after reading.

Read boundary

The local HTTP caller selects a host-installed provider ID and one event ID. These are selectors, not grants. The durable store must name that provider as an owner of the event's source. Unknown readers, revoked or stale ownership, receiver mismatch, disabled capture, and incomplete projections fail closed.

Pi user-text and requested-command readers keep their independent provenance, file fingerprint, parsing, redaction, and authorization proofs. The registry accepts only their safe, already-redacted output, caps provider output at 16 KiB, and the HTTP response clips to 4 KiB. Responses are local-only and no-store; receiver and source revision changes cancel delivery. The UI keeps preview text transiently for at most 20 seconds.

Extension boundary

Only trusted receiver composition can install a read provider or UI preview declaration. Children, TOML, manifests, and arbitrary plugins cannot register readers or choose proof code. A future reader needs trusted proof and redaction logic plus a durable grant for the exact source. This does not let arbitrary plugins read private content.

Synthetic tests use fixed, non-sensitive text and cover exact source and receiver binding, unknown providers, provider RuntimeError isolation, revocation during reads, stale projections, and output bounds. Pi route tests cover 400 malformed input, 403 nonlocal access, 404 unavailable or revoked content, 409 mid-read changes, 503 unavailable revisions, no-store responses, and cancellation before response writing. UI tests cover transient preview expiry.

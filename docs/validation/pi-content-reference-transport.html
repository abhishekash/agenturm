Pi content reference transport checkpoint

Recorded 20 November 2026. This slice connects the receiver-owned Pi content reference gate to an explicitly configured, installed Pi directory process. It does not activate content capture by default. The bundled Rust Pi reader still emits metadata-only batches, and no API, TUI, copy, or export path reads the content table. Python Store remains the sole writer.

Opt-in boundary

An operator must name a plugin manifest and configure capture = "pi-review-text-v1", replaces = ["pi"], an absolute directory root, the configured-source-read grant, and required source-discovery/1, source-discovery-root-gap/1, configured-root/1, and pi-content-ref/1 features. The manifest must claim those features and harness.pi/1; the running child must advertise them in its hello acknowledgment. A single-file Pi source or another harness cannot select this mode. The source ID has one reader owner; the trusted native Pi collector is excluded for the replacement. Config parsing remains inert.

The outer framed protocol remains version 1. Ordinary v1 batch messages and PollBatch validation stay strict. A content-mode child must add content_refs: {"schema_version":1,"refs":[...]} to every batch, including an empty list for idle polls. The envelope is separately versioned and accepted only after feature negotiation. It contains at most 48 reference objects and at most 64 KiB of encoded envelope bytes; the receiver's existing admission gate also caps nominated row bytes at 64 KiB and each row at 8 KiB. Missing, unknown, malformed, or unauthorized fields close the child without acknowledging the cursor. The reference carries only a source-relative path, byte range and hashes plus exact event, session, and turn identifiers; raw source text is not a permitted field. Content mode also requires source-discovery-root-gap/1 in the manifest, config, and hello, so the child can report root enumeration failure.

This schema is a receiver admission boundary, not a confidentiality sandbox for an untrusted executable. A malicious child with source-root access could encode text into permitted identifiers or write to stderr or another channel. The installed fixture proves only that its own frame carries references. Future content reads must independently recheck source availability and policy; a child-reported root gap alone cannot certify the current file. The current SourceLease/commit_batch write path checks receiver identity and epochs but does not bind a lease to the Store file's device/inode. A same-receiver, same-revision database replacement remains a separate admission and cutover gate; this transport does not close it.

The host constructs the capture fingerprint from its trusted configuration and no-follow source-root identity, activates the durable source with that fingerprint, and mints PiContentGrant from the issued lease. The child cannot supply the grant. A configured metadata-only restart activates with an empty fingerprint and logically removes prior content, receipt, and status in the same Store transaction before polling. A capture revocation also deletes SQL-visible content and fences the old lease. The Store keeps exact replay receipts: after a commit, the host acknowledges only the accepted cursor; a failed or mismatched commit sends no acknowledgment.

Installed evidence

tests/test_pi_content_transport.py installs a copied, SHA-pinned Python Pi directory child. The child reads one synthetic Pi JSONL row and sends only a hash/offset reference and content-free v1 message fact. The receiver opens the configured file itself, verifies the row against the member checkpoint, redacts a recognizable password assignment, and commits the content with evidence and cursor. The installed test covers idle polls, exact repeated-batch replay, supervisor wiring from parsed config, missing hello or root-gap feature, missing or malformed envelope, forbidden child text field, forged row hash, metadata-mode rejection, configuration downgrade while an old worker is live, and capture revocation. The sibling process/config/runtime/supervisor and receiver-content tests remain green in the focused run.

The installed child is a proof fixture, not the bundled Rust Pi emitter. The current Rust reader does not negotiate pi-content-ref/1 or produce content references. This slice does not establish native/process Review or export parity. Post-gap generations remain withheld as unanchored_origin; proof-budget, duplicate, invalidated-session, and capacity reasons stay partial. Redaction is best effort. SQL deletion does not sanitize SQLite WAL pages or backups.

Next gates

The Rust Pi directory adapter must emit reference-only envelopes under an explicit opt-in and prove its gap, pagination, and bounded source behavior through an installed corpus. A separate source-backed, policy-current Review reader and UI/export gate must verify source configuration, receiver, lease, policy, file identity, selected event and coverage at use time. Full Pi assistant/tool/branch parity and storage sanitization policy remain open. No performance gain or production default change is claimed.

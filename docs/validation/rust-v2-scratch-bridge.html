Feature-off v2 scratch admission bridge

The Rust scratch CLI can accept a typed v2 lifecycle request at an explicitly named disposable database. The storage service still serves v1 probes only. Python Store remains the production writer.

Boundary and transaction

The v2 frame contains no database path. --v2-scratch-path PATH supplies one outside the frame. The bridge requires an existing regular database with the explicit scratch marker before it acquires a cooperating writer lease. It then reuses the older scratch transaction’s receiver, source lease, capture policy, cursor, unsupported-history, evidence, empty-content receipt and dirty-sequence checks. The typed v2 parser adds a 64 KiB limit, closed lifecycle shape and canonical request digest.

For v2 only, the same transaction records the request ID, receiver and source, request digest, cursor, batch digest, first disposition and dirty sequence. Reusing an ID with changed content fails. An exact retry can replay only while the source lease and last-batch receipts are current. The reply binds the whole request digest to the transaction result. The v1 CLI remains compatible.

This is a scratch proof, not a production replay journal. Host-prepared digests remain untrusted assertions. The service has no v2 dispatch, canonical database, migration or recovery path. Python mutation routing, held-open legacy writer exclusion and all-database recovery remain cutover gates.

Verification

Installed process tests exercise commit, exact retry across CLI starts, conflicting ID, stale retry, malformed and unknown input, unmarked path, receipt tamper and capture revocation. CI builds the CLI and runs the installed scratch suite. Focused Rust tests, Clippy, formatting and Python process tests are local gates; GitHub CI status is reported separately.

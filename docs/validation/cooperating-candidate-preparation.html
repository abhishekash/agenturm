Cooperating candidate preparation

20 November 2026 · feature off

Coordinates supplied store instances and a dispatch guard before making an offline candidate. Python Store remains the production writer.

No authority transfer. Other instances, direct SQLite users, and old held-open processes still need independent exclusion. A verified candidate is not a cutover certificate.

Order and failure behavior

  1. Read-only preflight rejects invalid source, output, or verifier paths before any one-way fence; the producer rechecks after drain.
  2. Hold an exclusive outbound dispatch handoff guard bound to the supplied Store.
  3. Quiesce supplied WorkflowStore, TaskStore, and Store instances using one drain deadline. A failed drain makes no candidate and may leave one-way fences in place.
  4. While holding the guard, prepare detached backups and invoke the Rust verifier. Recheck the guard before returning.
  5. If the guard fails after backup verification, mark the candidate incomplete or remove its marker and sync the directory; require manual quarantine if durable invalidation fails.

The timeout bounds the drain, not backup or verifier runtime.

Validation

Nine real-store integration tests cover success, retained fences, active dispatch, held workflow and telemetry connections, wrong outbound Store, invalid input preflight, guard lifetime through backup, and late guard and marker-sync failures. The installed fixture invokes the Rust verifier. GitHub CI results are separate and may still be queued.

Remaining gates

The guard excludes cooperating dispatch and reconciliation, but does not settle uncertain deliveries. Each store drain is instance-local. Direct CLI and SQLite paths, other instances, old binaries, service permissions, canonical publication, crash recovery, and forward-only Rust writes remain open.

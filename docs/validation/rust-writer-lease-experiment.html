Rust cooperative writer lease experiment

Agenturm validation · 20 November 2026

This Linux-only crate is feature off. Python Store remains the only production database writer. The receiver, launcher, plugin host and scratch-admission CLI do not call it.

Contract

WriterLease::acquire binds an existing absolute fixture path, its lexical symlink, resolved regular target and device/inode, plus a private sibling lock derived from that target. It rejects multiply linked database inodes so hardlink aliases cannot select different locks. It rejects existing nonregular lock entries before open, then uses nofollow, nonblocking and close-on-exec flags, verifies owner-only permissions and pathname identity, and takes a nonblocking standard-library file lock. Repeated acquisitions within one process share the same open descriptor until the final handle drops.

verify_admission() checks the lock pathname, database path and target link count again immediately before a prospective write. Lock-file replacement, a new hard link, symlink retargeting and database inode replacement cause the next admission to fail.

Focused tests

  • Two processes, including a database symlink alias, cannot hold the same cooperative lock; fixture bytes and SQLite sidecars remain untouched.
  • A hardlink alias cannot derive another lock for the same inode, and adding a hard link invalidates the next admission.
  • Same-process handles retain the lock until the final drop; killing the owner releases it.
  • Symlinked, nonregular, nonprivate or replaced lock files fail, as do changed database targets.

Limits

The check is point-in-time. It does not stop an already in-flight write or an old binary that ignores the lock, and it does not exclude a deliberate swap-and-swap-back race. Manual fork with an inherited handle is unsupported; exec closes the descriptor. No Store worker quiescence or production cutover is implemented, and no performance gain is asserted.

See the writer cutover gate for the remaining legacy-binary and recovery requirements.

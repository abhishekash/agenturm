# Experimental v2 scratch service checkpoint

20 November 2026. This is an opt-in Linux storage-service experiment. It does not enable a production Rust writer, migrate a canonical database, or connect the service to the receiver.

The ordinary service mode remains a v1 protocol probe with an empty, service-owned `0700` data root. The explicit `--experimental-v2-scratch enabled` mode uses one fixed, pre-existing `scratch.db` in that root. The v2 client frame has no database path. The service requires a service-owned, singly linked `0600` regular scratch file, the `storage_admission_scratch_v1=enabled` marker, and a separate `2710` transport directory with a `0660` socket. It takes its persistent instance lock before the SQLite marker preflight and holds a `077` process umask in scratch mode, so new SQLite sidecars stay private even under a permissive launcher umask. The private root admits only the scratch file, its known SQLite sidecars, and its private writer-lease file; it pins the scratch inode across requests.

The service checks Linux `SO_PEERCRED` before reading untrusted bytes, accepts one bounded 64 KiB v2 frame per connection within a two-second total frame deadline, and verifies the receiver identity. It passes only that typed request to the existing scratch admission transaction, which rechecks source lease, capture policy, cursor, evidence, marker and replay identity. The v2 reply is validated against the request before framing. A failed admission sends no reply. If a post-commit path or socket check fails, the durable scratch receipt remains but no reply is sent; an exact retry is the recovery path after the service identity/path is restored, while a changed request ID or payload fails closed. Experimental mode rejects v1 probes; normal mode never dispatches v2.

Local validation: 27 targeted Rust unit tests across the contract, scratch admission and service; targeted Clippy with warnings denied and workspace formatting; 10 existing installed service tests, 13 existing installed scratch CLI tests; and both root-required disposable Docker account fixtures in a bare Python 3.12 image with no network. The v2 fixture proves a valid commit, exact replay, conflicting request ID, wrong receiver, wrong UID/GID, same-UID denial, oversized/v1 rejection, fresh old-Python-Store denial, unchanged unrelated canonical sentinel, pinned-path replacement refusal, extra private-root file rejection, missing scratch-marker rejection, and an exact retry after a deliberately discarded reply. The fixture starts the service with inherited umask `000` and checks every resulting scratch file is service-owned `0600`. The default v1 account fixture still passes. GitHub CI runs the new fixture but its result must be reported separately from these local checks.

This is a disposable scratch writer only. It does not cover all Python mutation paths, existing old binaries with held-open handles, durable workflow/task/outbound state, production migration or WAL recovery, or cross-platform service principals. Those gates in the [writer cutover plan](rust-writer-cutover-gate.md) remain required before canonical Rust authority.

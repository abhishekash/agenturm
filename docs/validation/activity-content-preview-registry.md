# Trusted Activity content-preview providers

Recorded 20 November 2026. The cockpit keeps the existing explicit `z` preview for one Pi user message. A bounded, trusted `ContentPreviewRegistry` now selects a provider for an exact Activity row. The built-in Pi provider supplies eligibility, a same-origin `/api/plugin-…` path, and inspector labels. A trusted caller may inject another provider at app construction without editing the central Activity inspector. Ambiguous matches, nonlocal route shapes, malformed IDs and invalid provider output fail closed; a provider's exact receiver route must be registered separately.

The shell still owns the security lifecycle: it checks the current receiver and exact Activity revision before and after the HTTP call; the receiver independently proves source and policy again before response headers. Only a sanitized, 4096-byte response field enters transient inspector state. The preview clears on selection, receiver, provider or tab change, revocation recheck, and 20-second expiry. RichLog's rendered strips and the inspector cache are cleared together. Copy, export, ReviewHistory and Activity rows remain content-free. A point-in-time preview can remain visible until its 20-second expiry if the underlying same-inode source is edited after loading without an Activity revision change.

The new provider contract is in-process and trusted. It does not discover external UI plugins, expose a Pi requested-command read API, register a command provider in production, or relax the receiver's source gate. A later command provider must supply its own reviewed exact-event HTTP route; this PR only proves the UI extension point with a fixture provider.

Validation: headless Textual tests exercise the fixture provider and stable masthead at 60×18 and 80×24, explicit `z`, unavailable and loaded states, and selection clearing. Unit tests cover unique selection, ambiguous provider denial, route validation, exact receiver/revision response acceptance, and copy/export isolation. Existing Pi preview delivery and revocation tests are rerun after the refactor.

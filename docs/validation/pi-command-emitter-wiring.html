Opt-in Pi requested-command reference emitter

The default process reader is metadata-only. User-text and requested-command modes are mutually exclusive. Python Store remains the sole production writer for the receiver database. No performance gain or full Pi parity is claimed.

Boundary

--directory --command-refs installs a separate source ID, capture mode, feature and SHA-pinned Rust binary. The host requires the Pi replacement claim, configured root, read grant and discovery features before minting a command grant. The child emits only exact row and tool-block references in a versioned command_refs envelope; no command or argument bytes are sent.

The Rust reader nominates a bash tool call only when a same-batch started shell fact, bounded source prefix, member generation and preceding user turn agree. The host independently proves the source with no-follow reads, durable checkpoint, row hash, block, timestamp and turn. It stores at most 4 KiB of best-effort redacted requested command text. A started fact means Pi recorded a request; it does not prove execution or success. Tool-result text and non-bash calls cannot nominate command text.

Idle and gap batches carry empty command envelopes. Gaps invalidate content; exact replay checks receipts, and capture revocation removes rows and receipts. Ordinary Activity, copy and export remain content-free. There is no command-specific HTTP, TUI, Review, copy or export read path. Logical deletion does not sanitize SQLite pages, WAL or backups.

Verification and next gate

Rust and installed receiver tests cover exact references, prior acknowledged turns, metadata default, mutually exclusive modes, idle/root-gap shape, non-bash and result-only negatives, Activity/copy output, replay and revocation. Existing Pi content and transport suites guard compatibility. A later read/delivery gate must bind the selected Activity item to current policy and exact source proof before a preview labeled Requested shell command can appear.

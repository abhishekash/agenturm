# Rust Claude Code process reader vertical slice

Recorded 20 November 2026. This checkpoint adds an opt-in, separately installed Rust reader for one explicitly configured Claude Code **main transcript** JSONL file. It uses the shared bounded JSONL process runtime and the existing host-owned manifest, admission, policy, cursor and projection path. The native Claude Code reader remains the default. This is not a performance claim or a full replacement.

## Evidence and bounds

The first complete row must carry a valid `sessionId`. The reader emits content-free user and assistant message facts, coarse tool start/result facts with opaque operation correlation, selected reported usage counters, and lifecycle facts. Only an explicit assistant `stop_reason=end_turn` reports Completed. A user turn, tool call or result, and assistant work without that terminal marker report Running. Silence, process exit, a PR, and an unsupported stop reason never establish completion or interruption. Unsupported rows, content blocks and stop reasons produce coarse diagnostics. Claude tool results commonly omit `is_error` for success; the reader treats absence as success and rejects a present non-boolean value before cursor acknowledgment.

The reader never sends prompt text, response text, tool arguments, output, command names, model names, working directories or source paths into Agenturm's Store. It hashes row, turn, message and operation identifiers where needed and sends only typed metadata. An installed receiver test compares the supported terminal state and usage totals with the native Claude Code reader, proves two tool phases share one operation key and one turn, and checks that private strings do not enter Activity or admitted payloads. It emits no check fact because Claude transcript tool results do not by themselves prove that a test, lint, build or review check passed.

Claude's reported input total includes `input_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`; cache components are also retained separately. Repeated rows with the same assistant message ID correct one usage event using increasing byte-offset revisions. The durable cursor checkpoints the maxima for the most recent message ID, so a lower streamed update after restart cannot lower those counters. This small checkpoint does **not** prove max-usage parity if an older message ID returns after a different one. A source offset beyond the protocol's `2^31−1` revision limit fails before acknowledgment. Distinct source generations separate event IDs after detected replacement, truncation, header change or checked-tail rewrite. A gap is diagnostic and does not erase previously admitted same-session evidence; totals across a rewritten source therefore remain partial.

The configured source is a single append-only file, capped at 1 MiB per line and scan, 256 records per poll, 8,192 structural JSON tokens per batch and a 512-character durable cursor. The reader requires a `sessionId` in the first row and does not discover project directories, decode Claude sidecar subagent relationships, preserve all model/Review detail, or certify every Claude producer version. Unsupported content remains visibly incomplete. The documented `serve --no-local-agents --plugin-config` invocation avoids dual reading in the demo by disabling all bundled native local-agent readers; it is not a production replacement switch. The Python Store remains the sole database writer.

## Verification

The installed SHA-pinned binary tests cover native terminal and usage conformance, content exclusion, tool/turn correlation, repeated usage correction across restart including a lower update, same-inode rewrite generation, capture revocation, malformed result refusal before ack, unsupported-row diagnostics and installer symlink refusal. Rust unit tests cover payload privacy, durable max checkpoint validation, unsupported-stop coverage and the revision bound. CI builds the binary and runs the installed receiver tests alongside workspace formatting, Clippy and Rust tests.

Receiver fenced capability Activity

Recorded 20 November 2026. This checkpoint tightens the opt-in, separately installed Prompt signals process. Its worker now requests capture_scope=1 on the existing Activity endpoint. The ordinary Activity API keeps its previous behavior.

Authority and result

The receiver requires one exact service, session and agent, a bounded page, no subtree or Review widening, and an explicit content-capture grant in its live local collector status. Every matching health row must identify an evidence source; generic reader rows carry evidence_source_id when their display ID differs from the source that wrote Activity. A registered source connection with capture_content=false denies the request even while collector status has not refreshed. SQLite triggers advance a global capture policy epoch when a source connection is added or removed or its capture flag or service changes. The epoch, current source flags, collector instance, and approved source set form the request's policy token; a revoke followed by a quick regrant cannot validate an earlier request. Ordinary heartbeat updates leave the epoch unchanged. The nine-column connection table remains compatible with existing writers.

The Activity SQL read admits only rows whose persisted log or span provenance names an approved source and carries a host-owned row mark from accepted NativeEvidenceFacade ingestion. Raw span/log inserts, updates and deletes clear that mark; a trusted native write restores it in the same Store transaction. An authenticated OTLP or /api/spans writer cannot gain capability authority by copying observatory.source_id and scope_name. It materializes at most the newest limit + 1 candidate rows before filtering; this caps owner lookups and returned data, while SQLite may still seek through a larger actor/session index range. No query-time performance claim is made. Missing or different source ownership within that bounded window rejects the scoped read. Older rows cannot produce a complete aggregate while more than limit approved rows are present; that window is marked degraded. Plugin sessions remain metadata-only and cannot grant this capability. Existing native rows written before this provenance mark are denied until a trusted writer commits a new row for them; an unchanged no-op poll does not confer provenance. No origin is inferred from historical attributes. Scoped requests bypass the ordinary Activity response cache because native capture can change in memory without a SQLite write. A request-local, read-only SQLite connection compares PRAGMA data_version before the Activity read and at the final send guard, catching a raw change committed during the read even if the capture flag stays true. It holds no read transaction and closes on every response path. The receiver also rechecks the policy token. A change observed during the request yields an error with no Activity data.

The cockpit still checks its Feed snapshot without blocking Textual, and its worker still checks live health around the receiver request. These checks hide a cached pane when the Feed observes a denial. A receiver 409 invalidates the current approval and lets the health watcher recheck; it does not permanently disable the pane merely because another source changed. An explicit 403 denies the scope. The receiver check linearizes a successful request at its final policy read. A grant revoked after the receiver starts sending cannot retroactively remove bytes already delivered; the cockpit's nonblocking watcher and Feed denial remain responsible for hiding a previously rendered model. Native collector/session capture flags are fixed for that collector lifetime, except a one-way internal review denial. Unknown external SDK source provenance is excluded from the scoped capability rather than treated as captured content.

Verification

The installed real receiver test covers an exact agent among more than 200 sibling events, source denial before the read, an in-memory native denial after a warm response, revoke/regrant during a held Activity read, a new untrusted row and replacement of a marked span during held reads, an authenticated HTTP source-identity collision, raw replacement of a marked log, trusted re-poll restoration, revision-watch failure and closure, and continued ordinary Activity pagination. A separate test proves the watch observes other connections’ commits without pinning a WAL snapshot. Another proves a stale native generation rejected by the Store cannot restore a removed provenance mark. A process-pane test recovers after one receiver 409; focused capability and OpenCode tests exercise generic reader source binding and existing UI behavior. The process still receives only bounded aggregate counts, never prompt text, commands or Activity payloads.

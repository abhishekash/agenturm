Rust migration candidate verifier

20 November 2026 · feature off

A read-only inspection of three detached SQLite backups. Python Store remains the production writer.

Authority has not changed. The verifier cannot publish a database, flip an authority marker, archive old files, create a target, or exclude a held-open old writer.

What it checks

  • One trusted migration_manifest_v1 with required telemetry, workflow, and saved-task backups; unknown fields and versions fail.
  • Absolute paths, device and inode, size, SHA-256, private regular files and directory, and absence of SQLite sidecars.
  • Immutable, query-only SQLite reads, quick_check(1), and a second byte digest after inspection. Linux binds SQLite to the checked descriptor.
  • Global and per-source receiver identity; telemetry read contract 1, workflow schema 2, task schema 1; exact bounded source cursor and replay claims, workflow counts, task count and maximum revision.

Validation

Focused Rust fixtures cover a committed WAL-only row in the SQLite backup, tampered or replaced backup, wrong global or source receiver/schema/receipt/count, missing auxiliary database, symlink and public file, unknown field, and interrupted preparation that leaves the live source intact. An installed Python fixture confirms acceptance of detached backups from actual Store, WorkflowStore, and TaskStore instances.

Cutover work still required

The manifest is trusted input. Counts do not prove every receipt, and the verifier does not prove the three backups share a stopped-write epoch. A real cutover still needs old writer exclusion, complete mutation-path drain, authenticated backup production, protected service ownership, recovery, and platform qualification. Non-Linux Unix lacks the Linux descriptor-bound SQLite open guarantee.

Read the writer cutover gate for the remaining acceptance criteria.

Rust writer cutover: ownership gate

Agenturm architecture checkpoint · 20 November 2026 · current through PR #243

Decision: Python Store remains the only production writer. A cooperating lock is a useful preparatory gate, but cannot prevent older same-user binaries from writing an accessible SQLite file. No performance or cutover result is claimed.

Current write topology

Store.__init__ performs authority preflight, then mutates file permissions, WAL mode and schema before starting workers. Each later Store._connect() opens a writable connection. The standalone receiver, cockpit LocalReceiver, and some direct CLI commands construct a Store; two processes can address the same database. Outbound delivery writes through Store. Workflow and saved-task databases are separate writer domains.

The storage_authority_v1 marker rejects a foreign owner in current Python startup, but it is a point-in-time check. Older binaries ignore it. Explicit --db symlinks are supported and can be retargeted. Read connections already check pathname identity on checkout; writer connections lack an equivalent lifetime fence.

Next bounded implementation

Cooperating lease

Acquire a nonblocking exclusive flock before Store construction. For the managed database, use observatory.writer.lock in the private state directory, opened O_NOFOLLOW | O_CLOEXEC | O_CREAT with owner-only permissions. Check regular file, owner, mode and descriptor/path identity before and after locking, and recheck descriptor/path identity on every writer admission.

Explicit path

For --db, derive a sibling lock from the resolved target so aliases contend. Bind both the lexical symlink and resolved database identity. A retarget or atomic replacement fails later writer admission. Share one lease through a process-ID and lock-inode registry across multiple Store objects in one process.

Limits

This is a cooperating process fence while the lock pathname stays stable, not a security sandbox or a stable SQLite handle under adversarial pathname swaps. Python sqlite3 does not expose its main-file descriptor. A Rust service should keep a long-lived writer connection and reject a canonical pathname that no longer names its bound database.

Release the lock only after proven quiescence. Today Store.close() uses bounded worker joins and can return with a worker alive; ReadConnections.close() does not await active read leases. A future lease must track active work and remain held until all writers and leases end or the process exits. A timeout must not release the lock while a worker can still write.

Keep the lease opt-in until cockpit fallback, standalone serve, and mutating CLI behavior are tested. Python clients must use the service API for all writes before Rust becomes the writer.

Lease acceptance tests

  1. Two new processes targeting the same managed database or a target/symlink alias: one acquires; the loser changes no main file, WAL, SHM, mode or marker.
  2. Two Store objects in one process share one lease; another process remains excluded until the last closes. Constructor failure releases it only after any started work has stopped.
  3. Owner SIGKILL releases the OS lock; restart recovers WAL and cursor/receipt without a concurrent second owner.
  4. Symlinked, nonregular or replaced lock-file path is rejected before database mutation. Unlink/recreate while the owner lives; its next writer admission must refuse the changed lock pathname. A write already in flight is not fenced by this check.
  5. Retarget an explicit database symlink or atomically replace the database while open: the next write fails and never recreates or adopts a new target.
  6. Exercise actual cockpit fallback, a receiver on another port, and mutating CLI commands; record clear behavior before making the lease default. Hold work beyond shutdown timeout and prove the lock remains held until quiescence or exit.

Legacy writer exclusion

An advisory lock and database marker bind cooperating clients only. A supported older process can ignore both. Triggers can block selected DML but cannot guard all DDL, trigger removal, or an existing open handle. Moving or changing permissions on a file does not revoke an open handle.

The cutover requires a new versioned canonical path protected by a distinct service principal and platform-qualified directory/file ACLs, with Python clients using the Rust API. Explicit or shared stores stay on Python authority until equivalent exclusion is proven. If deployment cannot enforce it, keep Python authoritative.

Adversarial acceptance runs each supported old wheel/CLI and direct old Store._connect() code against both canonical and archived stores. Attempt startup, DDL, DML and second accepted receiver creation. Check main file, WAL and SHM state, receiver identity and receipts. A successful legacy mutation blocks cutover.

Recovery boundary

Stop and identify old writers; take a consistent SQLite backup that includes WAL state; archive old files and sidecars under protected ownership. The first post-cutover Rust durable write is the point of no return. Before it, a verified snapshot may restore Python. After it, use forward recovery unless a lossless cross-version journal reconciles tasks, decisions, acknowledgements, configuration, policy tombstones and delivery state. Source replay cannot recreate them.

Open decisions

  • Which supported platforms can run an isolated storage identity with enforceable ACLs?
  • Which UI, CLI, workflow, task and outbound writes must become service API calls?
  • Which older executable artifacts are supported for migration and pinned in adversarial tests?
  • Should a second receiver attach to the active owner or fail before Store construction?

Full phase gates: Rust kernel plan. This report enables no Rust production write path.

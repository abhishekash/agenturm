Trusted capture-mode registry: first phase

20 November 2026. Explicit capture-mode selection now uses a receiver-owned, immutable CaptureModeRegistry across plugin configuration, supervisor and session startup. The default registry contains metadata-only, Pi user-text references and Pi requested-command references. Plugin TOML names a mode; it cannot install a validator or grant factory.

What the boundary checks

The registry checks required manifest features, configured grants, source root, replacement claim and mutually exclusive reference feature. Session startup repeats those checks against the trusted source before selecting the existing Pi grant class and fingerprint. Metadata-only remains the default.

A synthetic audit-only mode proves a second trusted mode can pass configuration, receiver composition and session selection. It has no reference feature, grant or private-content admission.

Remaining admission gate

The exact Pi source verifier, policy, lease, cursor, replay receipts, redaction and SQLite admission remain in Pi-specific modules and plugin_admission.commit_batch. BatchHandlerRegistry still selects wire envelopes. A new content-capable harness cannot admit private text through this first phase. The next SPI must move verified reference admission and durable receipts behind trusted host handlers while retaining every existing proof gate.

This is a configuration and session-lifecycle refactor. It does not enable a Rust production writer, claim a speed result or roll out a connector.

Validation

115 related plugin, process and admission tests passed, with 21 installed-binary skips. After receiver composition wiring, 36 focused Pi transport, registry, config, runtime and supervisor tests passed. With local Rust Pi and plugin-host binaries supplied, the 21 installed Pi content and command tests also passed. Tests cover the synthetic second mode, unknown modes, TOML validator injection, Pi reference-feature borrowing and a forged source policy.

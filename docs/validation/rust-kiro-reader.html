Rust Kiro process reader vertical slice

Recorded 20 November 2026. agenturm-kiro-harness is an opt-in, separately installed Rust reader for one configured Kiro messages.jsonl or sub-executions/<worker>.jsonl file. It uses the shared bounded JSONL process runtime, Python-owned policy and durable admission, and the existing content-free plugin fact contract. The built-in Kiro reader remains the default. There is no speed claim.

Kiro JSONL has no session header. The adapter derives a bounded native session or worker ID from the configured path and validates it before emitting facts. Its versioned k2 checkpoint binds a hash of that path, last turn, open-turn flag, one queued prompt, up to two pending interactions keyed by call ID and consent round, and up to four unresolved tool calls. Each new pending operation is keyed by a full SHA-256 of its exact call ID plus its coarse status and category; entries are serialized in deterministic key order. A duplicate pending call with identical represented status/category is an idempotent no-op; a duplicate key with changed status/category fails as ambiguous. A fifth unresolved call fails before acknowledgment. Results may resolve calls out of order. A new turn still fails closed while any prior call is unresolved; a late result after turn_end remains attached to its original turn. Old eight-field k1 cursors are restored and promoted to k2 on the next source checkpoint. A k1 cursor with an unresolved call necessarily retains its historical 96-bit call fingerprint until that result is consumed; new k2 calls use full 256-bit hashes. The Kiro checkpoint is capped at 524 bytes and the shared source cursor at 800 bytes, while source IDs remain capped at 200. A changed path to the same inode fails closed; a replaced inode or first-line rewrite emits a possible-gap diagnostic and advances the generation. The checkpoint never contains a workspace path, prompt, raw operation ID, or tool argument. A first line is both inspected for context and translated as evidence.

Evidence represented

Kiro observation Process fact
New user prompt, turn_start, explicit turn_end with end_turn, cancelled or error Content-free user message and running/completed/interrupted/failed lifecycle with explicit reason. A queued user prompt is held across restart until the next turn_start, then assigned to that turn.
assistant with operationType: Say Content-free assistant message. Other assistant operations produce a coarse diagnostic.
Tool call and result with an explicit success boolean or a call status of denied/failed; explicit policy denial metadata Correlated opaque operation IDs and coarse started/succeeded/failed/denied tool facts. A call's denial or failure takes precedence over a result's success: true. A result without success or a terminal call status fails before cursor acknowledgment.
Up to two approval or user-input interactions keyed by exact call ID and consentRound paused while any request remains pending, then running only after all matching resolutions. Coarse diagnostics record that decision details remain unrepresented. A third overlapping interaction fails before acknowledgment rather than inventing readiness.
Credit usage summary, subagent announcement or completion, and display error Coarse diagnostics indicating observed but unrepresented evidence. No prompt, command, path, output, credit amount or permission detail is stored in a process fact.

The current process usage schema accepts integer token counters, while Kiro reports credit units. The adapter emits kiro_credit_usage_unrepresented and leaves token usage absent; it does not turn credits into tokens or zero. The current lifecycle contract lacks native incomplete. An unknown turn_end.stopReason emits kiro_unknown_stop_reason and retains the prior reported state. The UI must treat this as partial coverage, not a successful end. Worker files are individually scoped; their exact parent and outcome require a second file and are not inferred from directory layout alone. The bounded cursor retains at most four unresolved calls and two simultaneous interactions; higher counts fail before acknowledgment.

Validation and remaining gates

The installed receiver test compares explicit Kiro stop status with the native reader, checks content-free message and tool Activity, verifies a real native credit span while the process leaves usage absent, exercises a queued prompt across restart, consent rounds across restart without false readiness, denied/failed call status against native results, late-result turn attribution with a fail-closed process boundary, worker path identity, result refusal, capture revocation, same-path replacement, symlink retargeting and installer symlink refusal. It also compares two overlapping operations resolved out of order across poll/restart, simulates Store commit followed by a lost ACK, and verifies duplicate/fifth-call failure leaves cursor and evidence unchanged. Rust unit tests cover path binding, k1-to-k2 migration, malformed and maximum-size checkpoints, four-call restoration, out-of-order resolution, duplicate/cap rejection, queued-turn and permission restoration, and terminal provenance. Workspace tests cover sibling harnesses.

Validation for this behavior slice: workspace formatting and Clippy passed; all 183 workspace Rust tests passed across 46 test binaries; the installed Kiro receiver suite, shared plugin-process/discovery checks and installed Pi/Codex/Claude/OpenCode regression suites passed 79/79 tests. The focused Kiro suite includes commit-before-ACK restart, out-of-order call results, denial/failure precedence, duplicate and fifth-call rollback, revocation/gap handling, and privacy checks. GitHub CI is queued for the PR; no remote CI result is claimed.

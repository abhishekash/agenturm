Rust cutover workflow inventory

Baseline is the Python v0.2.8 tag and the published Rust 0.3.7 Linux bundle. Rust 0.3.8 UI changes below are a candidate pending integrated qualification. The default switch requires the keyboard journeys and retained commands below to pass on the installed candidate. The Python comparison uses disposable 0.2.8 state. The Rust candidate uses a fresh Rust history directory and equivalent source fixtures.

The current implementation scope retains the remaining workflows. Remote receiver access, remaining eval views, automatic retention, recorded cost and historical host views are retained requirements. Their implemented paths and remaining gaps are listed below. The default entry-point switch stays gated while they and the paired keyboard journeys are incomplete. Rust supports explicit structural span imports into Rust history. Automatic migration of Python-era databases remains outside the Rust-only product scope.

Session task labels

The Rust Agents roster uses a saved task title when a session-level link matches the exact history, source, and session. If the bounded title read cannot resolve a single title, the roster can use a structural label such as a recorded pull request or file edit. Sessions without title evidence show Untitled session. The source and session ID remain visible separately.

Prompt and payload text stays in explicit private views. The live Python receiver client can label a row from typed activity and trace evidence tied to the same service, session, and actor. Legacy task fields can contain captured prompts, so the live roster leaves those fields outside its labels.

Attach to an existing Python 0.2.8 receiver

Use an authenticated Python 0.2.8 receiver already listening on loopback, or forward its port over SSH. Supply its URL-safe bearer token in an owner-only regular file. The Rust client opens the configured loopback socket directly. It neither discovers a receiver nor starts one. The protocol option must be explicit to attach to Python.

agenturm cockpit --endpoint http://127.0.0.1:14318 --token-file receiver.token \
  --receiver-protocol python-v0.2.8
agenturm cockpit --once --json --endpoint http://127.0.0.1:14318 \
  --token-file receiver.token --receiver-protocol python-v0.2.8
agenturm attention watch --once --endpoint http://127.0.0.1:14318 \
  --token-file receiver.token --receiver-protocol python-v0.2.8

The attached cockpit shows bounded live Agents, Activity, Traces and Pending pages. Enter on a session scopes the loaded evidence to the exact recorded service, session and actor where supplied. Escape restores the roster selection. The one-shot JSON response uses agenturm-python-receiver-live/1 and labels readiness and partial coverage. Reads check the receiver header and any body identity, then confirm the same health identity after the batch. The Python protocol provides live pages without a Rust history watermark. Private content, Review receipts, saved tasks and cross-host terminal routing are unavailable in this view. Client output excludes legacy prompt, log and arbitrary provider bodies.

Attention requires a ready, complete native lifecycle inventory. A partial or unavailable read leaves request state unconfirmed. A watch preserves the last exact pending evidence within its process and clears a request only when the same owner, sender and request record an ordered resolution. A missing request is insufficient. attention watch --once exits unsuccessfully if inventory cannot be confirmed. This mode creates no Rust history or durable workflow state.

Investigate retained failures

agenturm investigate failures --db history.sqlite --limit 50
agenturm broker investigate failures --broker-config broker.json --kind tool
agenturm investigate command 'cargo check' --failed --source-id harness.codex \
  --session-id session-id --db history.sqlite --config sources.json

failures scans authorized observation metadata, with optional exact --source-id, --session-id and --kind filters. Supported kinds are lifecycle, tool, mcp, check and trace. It reports explicit failed lifecycle and check states, failed or denied tool and MCP calls, and error span statuses. Eval outcomes are available separately through evals.

Each newline-delimited JSON page ends in a coverage record. --limit sets the number of observations examined, from 1 to 100. Pass next_cursor as --cursor with the same filters to continue at the pinned read snapshot. A page can contain zero matches and a continuation cursor.

Each candidate carries a reported result and exact occurrence metadata. Eligible Codex shell candidates include a source_reference. Open the reference with investigate source EVENT_ID --reference TOKEN and the appropriate local or broker configuration. Successful source inspection requires a current Codex command-detail grant and verifies the same retained occurrence and its terminal evidence. command --failed applies that same proof before emitting a matching invocation. Known informational exit-one commands, such as a plain rg with no matches, and contradictory terminal records are excluded from confirmed results. Receiver-wide discovery reads metadata. Phrase search of private evidence requires an exact source and session.

Open the cockpit in a new window

Run agenturm cockpit --new-window on Linux. From a tmux pane, the cockpit opens a window in that session. From a Linux desktop, it can launch GNOME Terminal, Konsole, or xterm when a display is available.

agenturm cockpit --new-window --db ./history.sqlite
agenturm broker cockpit --new-window --broker-config ./broker.json

The launcher keeps relative paths based on the original working directory. Local history, broker history, and cockpit --endpoint use the same options as in the current terminal. The command reports terminal launcher errors and returns the launcher's status. tmux returns after creating the window. The cockpit exits in the new window.

Use cockpit --once for a report in the current shell.

Import exported spans

Use import-jsonl with one exported native span object per line. The importer accepts a regular file or stdin (--file -) up to 4 MiB and 1,024 span records. It validates the complete batch before opening history for admission.

agenturm import-jsonl --file spans.jsonl --db history.sqlite --source-id otlp.exported

Rows carry trace_id, span_id, optional parent_span_id, start_unix_nano and end_unix_nano, and optional status (UNSET, OK or ERROR). Timestamps accept integers or decimal strings. IDs use 32 hexadecimal characters for the trace and 16 for each span. A parent outside the file is valid for a partial export.

A span needs an exact session ID from its attributes or the explicit --session-id argument. Span-level session aliases must agree, including session.id, gen_ai.conversation.id, and the legacy session, conversation and thread aliases. The argument fills missing session IDs and must match any IDs carried by the file. A native turn link requires agenturm.source.id and agenturm.turn.id. A worker link adds agenturm.worker.id.

The default import retains trace structure, timing, status, exact scope, and explicitly reported cost and token usage. Span names, events, links, and eval results are outside this import. Exact structural replays deduplicate across JSONL and OTLP JSON under the same source ID. Conflicting retained identities reject the entire import.

Use --payload-scope standalone to opt in to the two private text attributes agenturm.payload.input and agenturm.payload.output. Use --payload-scope harness.codex for rows that explicitly carry that agenturm.source.id. The session comes from an exact row attribute or the operator's --session-id. The scope flag must match the source of every captured span. Each slot is limited to 2 KiB and the captured text in a batch to 64 KiB. Invalid or credential-like selected text rejects the batch with an error that omits its contents.

agenturm import-jsonl --file spans.jsonl --db history.sqlite --source-id otlp.exported \
  --session-id demo --payload-scope standalone

Add --payload-format agent-harness to select the legacy agent-harness fields instead. For agent.run, agent.task and agent.summary fill Input and Output. For tool.call, the exported executed tool.arguments and tool.result fill those slots. Empty legacy slots are omitted. The format excludes proposed arguments, approval rationales, exceptions, other attributes, and event bodies. Agent-harness exports without a session ID need the explicit --session-id option.

Text is stored with its exact span occurrence in the private telemetry vault. A telemetry text grant is required to view it. Select capture on the first import. Replaying the same text deduplicates, changing the text or adding it to a metadata-only occurrence conflicts, and reimporting pruned text leaves it retired. Metadata queries and import output omit text.

The input JSONL remains a caller-managed file. Keep private exports in a directory accessible to the collector and use owner-only read permissions on the file, such as mode 0600. The vault grant controls access to the imported copy.

Publish live progress

The Python and Node manual SDKs publish Run.progress immediately to the Rust trace receiver. The progress route uses the same loopback authority and producer bearer as spans. The direct JSON route is POST /native/v1/progress with one event per request and a 4 KiB limit.

Each event carries a nonzero 32-digit hexadecimal event_id and trace_id, a decimal-string observed_at_unix_ns, and a public stage of 1 to 64 ASCII letters, digits, periods, underscores, or hyphens beginning with a letter. Send optional integer percent_basis_points from 0 to 10000. Each basis point is 0.01 percent. Zero is an explicit value and omission means unknown. The SDK sends no progress message or arbitrary attributes.

The receiver selects the storage source. A standalone receiver requires session_id. The launcher may supply its existing local run identity when the event targets no native harness. Native linkage uses an explicit session_id and target_source_id, plus turn_id and worker_id when applicable. Linked reads require a retained native anchor. The event ID is immutable within its storage source, including after retention expires the event.

Activity shows the retained events. Traces shows the latest report per exact scope on the loaded page, even while the parent span is still open. Progress records express reported stages and percentages. Span completion and native lifecycle state have their own evidence.

Reported token usage

OTLP JSON, OTLP protobuf and native JSONL retain explicit input, output, total, cache-read input, cache-write input, and reasoning-output token counts. The projector accepts supported gen_ai.usage.*, llm.usage.* and OpenInference llm.token_count.* fields, including the legacy explicit cache and reasoning aliases. The Python and Node producers forward the supported scalar counters.

Each counter accepts a nonnegative integer through the signed 64-bit limit. Zero is a reported value. Missing or invalid values and conflicting aliases leave that counter absent. Each breakdown keeps its originally reported units. The projector preserves the producer's input and output counts and records total only when supplied. A batch can contain up to 1,024 spans with cost and token usage evidence recorded beside each span in the same commit.

Workspace Usage and the originating OTLP session's Usage show the individual reports. query includes the source, exact session, trace and span, and any reported turn, worker and target harness. Aggregate usage views remain open for traces where multiple instrumentation layers report the same usage.

Reported cost

OTLP and native JSONL spans can carry agenturm.reported_cost.amount and agenturm.reported_cost.currency. The Rust-compatible Python and Node producers, including the Python OpenTelemetry metadata exporter, forward these fields as bounded scalars. The amount accepts a decimal string or number. The currency is a three-letter uppercase code. The receiver also accepts llm.cost_usd, llm.cost.total with llm.cost.currency, and gen_ai.usage.cost with gen_ai.usage.cost.currency. The agent-harness JSONL exporter calculates its leaf llm.cost_usd from its own price table. The importer keeps that producer-reported amount in USD. It omits agent.cost_usd and agent.usage.* run roll-ups, which can repeat the measurements on leaf spans.

Amounts use integer nano-units, with nine decimal places. Explicit zero is a cost record. Missing or invalid amounts, conflicting values, or an explicit llm.cost_known value other than true leave the span without a cost record. Query exposes each record's source, exact span, currency and decimal-string nanounits. Workspace Usage and the originating OTLP session's Usage show the amount and currency beside the source evidence. Multiple spans can repeat a report, so Usage shows individual records and leaves totals open. Kiro credits use their native credit unit. Agenturm does not derive an amount from tokens, model prices, or credits.

The native Pi and OpenCode adapters also retain terminal assistant-message cost reports in USD. Pi reads message.usage.cost.total with basis estimate unless Pi explicitly marks totalFromProvider: true. Those records carry basis provider_reported. OpenCode reads the completed assistant message's cost with basis unknown, since the stored amount can come from either endpoint accounting or OpenCode's rate estimate. Pi cost contract · OpenCode assistant schema · OpenCode cost selection

Native records expose native_origin.basis, native_origin.rounded, the retained revision and an operation ID that identifies the associated assistant event. Amounts round to the nearest nano-unit. Positive amounts that would round to zero are omitted, preserving the distinction from an explicit zero. Usage shows the individual reports in the selected history page. Forks can copy assistant histories and telemetry can repeat the same provider report, so a combined cost total remains unknown.

Import evaluation results

Import the spans first, then select their exact OTLP source for the outcome import and lookup. These commands also support --broker-config in place of --db. A broker collector can import only into an allowlisted source. Collectors and readers can read the outcome for an allowlisted source.

agenturm import-evals --file results.json --db history.sqlite --source-id otlp.exported
agenturm evals --db history.sqlite --source-id otlp.exported \
  --trace-id 11111111111111111111111111111111 --json

The importer accepts a regular results.json file or stdin (--file -) up to 4 MiB. The top-level results array accepts up to 1,024 outcomes. Each outcome requires a 32-character hexadecimal trace_id and a boolean passed. Optional fields include task_id, provider_model and up to 32 scores. Each score supplies a scorer plus a boolean passed, a numeric score, or both. Metadata labels allow up to 128 ASCII characters. They start with a letter or digit and can also contain ._:/@+-. The importer rejects recognized credential prefixes in metadata labels. Metadata is the default import. Optional private capture is described below.

Every result must match a retained trace under the selected source ID. Duplicate trace IDs within a batch or a missing match reject the whole batch. Evaluation pass/fail is independent of the execution status of the spans. Corrected metadata advances the outcome revision. An exact replay of any previous revision leaves the latest outcome unchanged. Plain evals prints the current outcome and --json returns its metadata or null. SQLite backups preserve outcomes and replay receipts. Pruning removes outcome metadata when the trace loses its last retained span in that source. Retained digests and revision numbers prevent an old import from reviving the outcome if a new span arrives under the same trace ID. Read retained revisions with evals --trace-id <id> --history. Use --limit 1..256 and the returned --before-revision cursor to continue. evals --summary lists the latest outcome per retained trace in the selected source and counts passes and failures on that page. Its --after-trace-id cursor continues in trace-ID order. JSON includes the page and continuation fields. These views read current state on each invocation; concurrent changes can change a later page. Counts describe the displayed page, not a whole-history total. Pruned bodies stay absent from both views even if a trace ID reappears. The same options work through the broker and keep its source allowlist.

Use evals --list with one to 16 distinct --source-id flags for a complete, bounded inventory of current outcomes. Each result identifies its exact source, trace and latest retained revision. The same trace ID can appear independently in different sources. All results share the transaction's trace evidence snapshot, and evaluation metadata reflects current revisions at that read.

agenturm evals --list --db history.sqlite --source-id otlp.exported \
  --source-id otlp.ci --json

The inventory checks up to 1,024 candidate source/trace keys, including retired keys kept for replay protection, and allows up to 2 MiB of serialized rows. If either limit is exceeded, the command fails without a partial inventory. The list includes neither private text nor private reveal selections. Broker CLI and authenticated HTTP inventory

Private evaluation text

Use --include-detail to capture the error string on a result and the detail string on each score. The capture records the original score position. The allowed fields accept up to 2 KiB each, 4 KiB per result and 64 KiB per import. Scalar text is the supported format. A credential-like or unsafe string rejects the batch before any result or detail commits.

agenturm import-evals --include-detail --file results.json --db history.sqlite --source-id otlp.exported
agenturm eval-detail grant --db history.sqlite --source-id otlp.exported
agenturm eval-detail preview --db history.sqlite --selection selection.json
agenturm eval-detail revoke --db history.sqlite --source-id otlp.exported

Copy the detail_selection object from evals --json for the exact revision into selection.json. It contains the source, trace, revision, receipt ID and snapshot. The receipt is issued with the new result revision and preserves the original capture across retries. Reusing the same metadata with supplied details requires the exact original capture. Capturing detail for an existing metadata-only result requires a distinct corrected metadata revision. Replay preserves the current version and leaves expired text unavailable.

Disclosure requires an eval.result_detail approval for the exact OTLP source. The viewer verifies the capture receipt and its supporting retained trace occurrence at the supplied snapshot. Pruning that supporting occurrence removes the text and preserves the outcome's revision and detail digest. Restored backups require fresh approval and a fresh snapshot. Metadata views only return result metadata and the selection reference. See broker evaluation detail commands.

In the cockpit, press E from global or session Traces to choose a trace on the loaded page. The picker preserves its selection by exact OTLP source and trace ID, including when two sources report the same trace ID. Enter opens the retained revisions and marks the current one. The detail shows the execution status counts for the loaded spans alongside the separate evaluation verdict. Page Up and Page Down scroll task, model and scorer metadata. Missing score values appear as unknown.

Press s for the source's current outcomes, or ] to continue when another page is available. Escape returns to the revision, trace selection and Traces views in order. The loaded trace snapshot establishes its identity. Each evaluation request reads current retained metadata from that history and fails when the selected snapshot has expired or the receiver has restored a different branch. This metadata view also works through the broker and the authenticated HTTP reader for allowed OTLP sources.

In the local or broker cockpit, select a revision marked d private to open its imported evaluation text. Escape clears the private view and returns to the same selection. The private view uses the current approval and expires after 25 seconds.

Task Git patches

Save a patch from the Linux checkout attached to a task. The optional revision checks which version of the task receives the capture. The command reports the updated task, Git summary, and saved patch byte count.

agenturm task snapshot 42 --db history.sqlite --expected-revision 3 --include-diff
agenturm task handoff 42 --db history.sqlite --include-diff --format json
agenturm task handoff 42 --db history.sqlite --include-diff --output ./handoff-42

The patch has separate staged and unstaged sections for tracked files. Git records binary changes as notices. Untracked files contribute only to the summary count. Capture uses detached Git configuration, a sealed index copy, and bounded regular-file inputs. Git hooks, filters, external diff drivers, text conversion and submodule traversal are disabled during patch generation. The patch accepts display-safe UTF-8 up to 64 KiB combined across 64 changed paths and 8 MiB of file and Git blob inputs. A changed HEAD or index, a split index, an unsupported path, or a limit failure leaves the task unchanged. Concurrent changes in the checkout can require another capture.

The patch stays in the private workspace ledger and its portable backups. Only handoffs with --include-diff read the patch for display or export. --output writes a new private directory with Markdown and HTML. A plain snapshot or a workspace remap clears the previously saved patch. Broker task commands use the same options with --broker-config and capture from the client's checkout.

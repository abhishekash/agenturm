Import exported spans

Use import-jsonl with one exported native span object per line. The importer accepts a regular file or stdin (--file -) up to 4 MiB and 1,024 span records. It validates the complete batch before opening history for admission.

agenturm import-jsonl --file spans.jsonl --db history.sqlite --source-id otlp.exported

Rows carry trace_id, span_id, optional parent_span_id, start_unix_nano and end_unix_nano, and optional status (UNSET, OK or ERROR). Timestamps accept integers or decimal strings. IDs use 32 hexadecimal characters for the trace and 16 for each span. A parent outside the file is valid for a partial export.

A span needs an exact session ID from its attributes or the explicit --session-id argument. Span-level session aliases must agree, including session.id, gen_ai.conversation.id, and the legacy session, conversation and thread aliases. The argument fills missing session IDs and must match any IDs carried by the file. A native turn link requires agenturm.source.id and agenturm.turn.id. A worker link adds agenturm.worker.id.

Imports retain trace structure, timing, status and exact scope. Import discards span names, payloads, events, links, token usage, cost, and eval results. Those legacy fields and workflows have separate cutover coverage. Exact structural replays deduplicate across JSONL and OTLP JSON under the same source ID. Conflicting retained identities reject the entire import.

Import evaluation results

Import the spans first, then select their exact OTLP source for the outcome import and lookup. These commands also support --broker-config in place of --db. A broker collector can import only into an allowlisted source. Collectors and readers can read the outcome for an allowlisted source.

agenturm import-evals --file results.json --db history.sqlite --source-id otlp.exported
agenturm evals --db history.sqlite --source-id otlp.exported \
  --trace-id 11111111111111111111111111111111 --json

The importer accepts a regular results.json file or stdin (--file -) up to 4 MiB. The top-level results array accepts up to 1,024 outcomes. Each outcome requires a 32-character hexadecimal trace_id and a boolean passed. Optional fields include task_id, provider_model and up to 32 scores. Each score supplies a scorer plus a boolean passed, a numeric score, or both. Metadata labels allow up to 128 ASCII characters. They start with a letter or digit and can also contain ._:/@+-. The importer rejects recognized credential prefixes and discards producer errors, score detail text, inputs, outputs, and other result fields.

Every result must match a retained trace under the selected source ID. Duplicate trace IDs within a batch or a missing match reject the whole batch. Evaluation pass/fail is independent of the execution status of the spans. Corrected metadata advances the outcome revision. An exact replay of any previous revision leaves the latest outcome unchanged. Plain evals prints the current outcome and --json returns its metadata or null. SQLite backups preserve outcomes. Pruning removes the outcome and its revisions when the trace loses its last retained span in that source. Aggregate evaluation views, revision browsing, and private result detail remain outside this implementation.

Task Git patches

Save a patch from the Linux checkout attached to a task. The optional revision checks which version of the task receives the capture. The command reports the updated task, Git summary, and saved patch byte count.

agenturm task snapshot 42 --db history.sqlite --expected-revision 3 --include-diff
agenturm task handoff 42 --db history.sqlite --include-diff --format json
agenturm task handoff 42 --db history.sqlite --include-diff --output ./handoff-42

The patch has separate staged and unstaged sections for tracked files. Git records binary changes as notices. Untracked files contribute only to the summary count. Capture uses detached Git configuration, a sealed index copy, and bounded regular-file inputs. Git hooks, filters, external diff drivers, text conversion and submodule traversal are disabled during patch generation. The patch accepts display-safe UTF-8 up to 64 KiB combined across 64 changed paths and 8 MiB of file and Git blob inputs. A changed HEAD or index, a split index, an unsupported path, or a limit failure leaves the task unchanged. Concurrent changes in the checkout can require another capture.

The patch stays in the private workspace ledger and its portable backups. Only handoffs with --include-diff read the patch for display or export. --output writes a new private directory with Markdown and HTML. A plain snapshot or a workspace remap clears the previously saved patch. Broker task commands use the same options with --broker-config and capture from the client's checkout.

# Pi content reference admission gate

Recorded 20 November 2026 as an **internal, feature-off primitive**, not a new Pi Review or export feature. The [later opt-in transport checkpoint](../validation/pi-content-reference-transport.md) adds a separately versioned reference envelope and explicit configuration for an installed Pi directory process; the bundled Rust Pi reader remains metadata-only. No API, TUI pane, copy command, or export reads the content table. The Python Store remains the only database writer. This gate establishes what an opted-in Pi directory content path must prove before any Review surface can consume it.

## Current parity boundary

The trusted native Pi adapter can capture a user's text, tool call arguments, and tool result text into bounded Activity when detail capture is enabled. Native trace and Activity readers can then contribute to existing review and export flows. Its assistant text is not a general Activity message; tool calls and model usage are emitted from assistant rows. The Rust Pi process reader translates Pi JSONL to content-free v1 message, tool, usage, lifecycle, and diagnostic facts. The receiver projects partial Activity and a session state from those facts. It has no content-backed process turn Review, no native trace membership, and no content export.

| Corpus case | Native Pi path | Current process path | This gate |
| --- | --- | --- | --- |
| User text with a recognizable credential | Captured Activity detail if enabled, passed through native bounded best-effort redaction | User role only | Receiver independently reads one exact source row, applies the same best-effort text redaction, stores a bounded internal row |
| Assistant tool calls and arguments | Call Activity can include captured arguments | Coarse category, operation ID, started | No content reference kind yet; future separate grant and parity proof |
| Tool result and late result after a later user turn | Native adapter uses its retained call map, falling back to current turn when no call remains | Receiver derives `matched_call` only from one retained earlier call; missing/ambiguous relations stay uncertain | No tool content or association claim |
| Branch/edit/unsupported Pi rows | Native reader may update session metadata or ignore unsupported kinds; it does not make every row an edit proof | Coarse `unsupported_pi_row` diagnostic | No content capture or complete-coverage claim |
| Rewritten, removed, or replaced member | Native and process readers each expose their own continuity limits | Member/root gap and Unknown state where affected | Existing content rows for affected sessions are logically removed; refs in a gap batch are withheld while metadata/cursor commit |
| Revoked source or changed capture configuration/root | Native policy and process source policy have distinct controls | Process metadata is deleted on capture revocation | Content rows and receipt are logically removed in the same relevant Store transaction; stale lease/grant fails |

The executable corpus is `tests/test_plugin_pi_content.py`, alongside the existing native/process comparison in `tests/test_pi_process_boundary.py` and installed Pi directory tests. Its synthetic Pi rows include a user message, duplicate native ID, gap/replacement, invalidated later turn, oversized proof prefix, secret assignment, forged time/revision/source reference, path traversal, symlink, FIFO replacement, config downgrade, root replacement, revocation, replay, and a stalled source read concurrent with a Store writer. The missing tool arguments/results, branch edits, and ambiguous call outcomes remain explicit later parity gates.

## Versioned opt-in envelope and trusted configuration

A separately negotiated transport now requires `pi-content-ref/1` in addition to `source-adapter/1`. Its envelope is **reference-only**: `schema = 1`, configured `source_id`, directory `member_id`, relative member path, byte offset and length, SHA-256 of the complete JSONL line, exact v1 `event_id` and revision, native session and turn IDs, and `kind = "pi.user_text"`. There is no raw text, tool argument, result, command, or arbitrary metadata field. The first slice is directory mode only. The current single-file Pi default has no source-root/member mapping for this contract and stays metadata-only.

A host grant is derived from trusted source configuration and manifest features, capture mode, artifact digest, allowed `configured-source-read` grant, configured root path, and the no-follow root device/inode. The source cursor stores a fingerprint of these inputs. A metadata-only activation passes an empty fingerprint; a change deletes retained content, receipt, and internal status before a new lease is issued. An artifact/plugin identity change still refuses activation until explicit source revocation. The transport now accepts an explicit content capture mode for an installed Pi directory child; the bundled Rust Pi reader does not yet send refs.

The receiver validates at most 48 references and 64 KiB of nominated rows per batch. Each row is at most 8 KiB. It walks every configured root and relative path component with `openat` and `O_NOFOLLOW`, opens the final regular `.jsonl` with `O_NONBLOCK`, and refuses traversal, symlinks, FIFO files, replacement roots, and changed file identity. The member ID must equal SHA-256 of the UTF-8 relative path, matching the Rust directory engine. The receiver checks the header, session/worker identity, current v2 member cursor device/inode, header hash, prefix hash and **canonical initial** JSONL generation derived from device, inode and header hash. It never trusts the generation string in a previously admitted metadata-only cursor as an attestation. For a continuous poll, it also proves the saved prior member cursor prefix and requires each referenced row to begin at or after that prior offset. It checks line boundaries, full row hash, Pi role and row ID, parseable timestamp and exact v1 time, revision zero, and `pi:{generation}:{row_id}:message`. One identical message fact must be in the same validated v1 batch. The process cannot authorize content by writing an extra v1 payload field.

File verification runs before the SQLite writer transaction. The receiver first reads the durable member checkpoint under a short read transaction, verifies the configured source file outside the writer lock, then compares that checkpoint, source cursor, lease, policy epoch, receiver identity, and content fingerprint again inside the existing `commit_batch` transaction. Metadata, content rows, cursor, receipt, and status commit together. A source file can change after this verification and before commit; the stored row is an admission-time, hashed observation, not a perpetual proof of the current file. A future Review read must add policy-current snapshot proof and handle source replacement explicitly.

## Storage and liveness

`plugin_content_v1` is keyed by source, hashed event ID, and revision. It stores source member ID, row offset/length/hash, source device/inode, native session/turn, receiver-redacted text, lease and policy epochs, and admitted sequence. It stores no raw JSONL line or relative path. `plugin_content_batch_v1` fences the exact refs digest at the last committed cursor so an ack crash accepts only an identical replay, even after the source file disappears. `plugin_content_status_v1` records the latest cursor, policy epoch, ref count and a closed reason: `none`, `not_requested`, `source_gap`, `proof_budget`, `unanchored_origin`, `duplicate_occurrence`, `invalidated_session`, or `capacity`. This is internal status; it is not a Review readiness claim.

The content proof prefix is capped at 8 MiB, intentionally narrower than the shared JSONL reader's source ceiling. A valid ref at a larger checkpoint is withheld with `proof_budget`, while metadata and cursor still commit. Malformed refs still fail admission. A source continuity-gap batch may contain both a diagnostic and new user facts; its refs are withheld with `source_gap` so it does not loop without acknowledgment. A later clean batch with a gap-derived generation is still withheld as `unanchored_origin`; a future host-owned attested generation ledger is required to resume content after that gap. A previously admitted, forged metadata cursor origin is withheld for the same reason. A repeated v1 occurrence cannot change prior content; a new ref for its duplicate ID is withheld with `duplicate_occurrence`. Tombstoned sessions cannot retain newly inserted content (`invalidated_session`). Oldest content rows are pruned if the 256-row or 1 MiB source cap would be exceeded; metadata continues and status says `capacity`. These are **partial coverage** rules, not claims that missing text can be reconstructed.

Capture revocation atomically removes content rows from SQL-visible tables, rotates lease/policy epochs and fences old workers. This is logical deletion, **not physical disk sanitization**; SQLite WAL/pages and backups may retain bytes. Physical sanitization and backup retention need their own policy before public content capture. Redaction uses the existing bounded native `plaintext`/`safe` rules and removes recognizable credential patterns on a best-effort basis. It cannot guarantee removal of every secret. Any future copy/export must show the exact selected content and revalidate receiver, source, lease, policy, file identity and revision at display and write; terminal selection and a saved file cannot be retroactively recalled.

## Exit gates before a public Pi Review slice

1. The separately versioned wire and explicit config opt-in have an installed synthetic child proof. Prove installed Rust Pi directory output omits refs for unsupported rows and safely handles gap, budget, and cap transitions; no v1 metadata field may become an implicit content channel.
2. Compare native and process results over a real Pi corpus with user/assistant messages, multiple tool calls/results, late and missing/ambiguous calls, branch/edit rows, malformed records, rewrite/delete/reappear, retention, and capture changes. State exact membership and coverage gaps.
3. Independently review the receiver-owned content read/provenance boundary, then add a policy-current query and UI/export proof that cannot copy stale content after revocation or source/config changes. Keep export a labeled frozen snapshot until a receiver-owned export transaction closes the final-check/file-create race.
